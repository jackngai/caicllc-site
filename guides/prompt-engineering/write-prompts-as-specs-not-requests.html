Prompt Engineering

Write Prompts as Specs, Not Requests

Good prompts behave like lightweight specifications: they define the job, expose context, set boundaries, force missing questions into the open, and make quality testable before the model starts producing work.

Updated June 25, 2026

Requests Create Guesswork

A vague prompt asks the model to infer the real task, the audience, the constraints, and the definition of done. Sometimes that works for low-stakes brainstorming. It breaks down when the output needs to fit a project, a workflow, a customer, or a decision. The model fills the gaps with plausible defaults, and those defaults often look competent enough to survive a quick read.

Write the prompt as a spec instead. Start with four fields: task, information, constraints, and ask. The task names the actual deliverable. The information gives background the model cannot safely infer. The constraints define format, scope, sources, tone, tools, exclusions, and risk boundaries. The ask tells the model what to do next, including whether it should answer, draft, critique, plan, or interview you first.

A weak request says, “Help me write a sales email.” A spec says, “Draft a 120-word follow-up email to a CFO who attended our demo, cares about implementation risk, and has not replied in eight days. Use a practical tone, avoid hype, mention the attached ROI worksheet, and end with one low-friction scheduling question. Before drafting, ask for any missing detail that would materially change the email.” That prompt gives the model less room to wander and more room to be useful.

Extract Context Before Output

The fastest way to improve prompt quality is to stop pretending you already know what the model needs. Add a clarifying question step at the start: “What do you need from me to give your best answer?” For complex work, make that an interview rather than a single question. Tell the model to ask one targeted question at a time until it understands the goal, constraints, audience, and edge cases.

This is especially valuable when the important context lives in your head: why a prior approach failed, what the team dislikes, which customer objections matter, which parts require human judgment, and which parts can be automated. Generic background produces generic output. Specific decision logic produces output that sounds like it belongs inside the work.

There is a tradeoff. Interviewing slows down the first response. Use it when wrong assumptions would cost more time than a few questions: implementation planning, customer-facing writing, automation design, sensitive analysis, or anything with a subjective quality bar. Skip it for disposable drafts and small transformations where the missing context is unlikely to matter.

Break Work Into Checkpoints

For large outputs, do not ask for the finished artifact in one pass. Use a research-to-outline-to-implementation flow. First gather or provide the source material. Then ask for a proposed structure, success criteria, and content requirements. Review that blueprint, trim weak parts, and only then ask for the full draft or build.

This pattern works because many failures are structural, not stylistic. If the outline is wrong, a polished final draft only hides the problem. Blueprint scaffolding lets you correct scope before the model spends effort generating details. It also makes success measurable: three practical takeaways, five sections, no claims outside the provided sources, objections handled from a CFO’s point of view, or a single HTML file with specified sections.

For complex projects, use small verifiable buckets. Instead of “build the dashboard,” specify “first define the data model and user actions, then draft the component plan, then implement the filter panel, then verify the empty, loading, and error states.” Checkpoints reduce context drift and make it easier to catch a bad assumption while it is still cheap.

Add Verification And Critique

A prompt spec should say how the output will be challenged. For factual or high-stakes claims, ask for verification through independent sources, external tools, logs, or multiple models where appropriate. The point is not to vote on truth by majority. It is to detect non-convergence: if several systems disagree or cite different assumptions, the claim needs human review.

For judgment-heavy work, use a critique pass. Ask the model to produce the draft from your intended perspective, then critique it from a concrete opposing persona: a risk-averse CTO, skeptical buyer, cost-focused CFO, strict reviewer, or impatient end user. Give that persona incentives and objections. “Find the parts that would make you say no” is sharper than “make this better.”

The critique must become an editing queue. After the red-team pass, ask the model to rewrite the weakest sections, remove unsupported claims, tighten vague language, or list unresolved risks. Do not accept a critique that merely comments on the draft. A useful critique changes the next action.

Save What Works

When a prompt produces a strong result after several rounds, reverse-engineer it into a reusable pattern. Ask the model to turn the conversation into a single prompt template with placeholders, required inputs, constraints, quality checks, and known pitfalls. This converts one successful session into an asset instead of leaving it buried in chat history.

Reusable prompts should include “gotchas.” Capture the edge cases that caused bad output: too much jargon, claims beyond sources, overlong sections, missing counterarguments, brittle code assumptions, or tone that sounds like marketing copy. These details are often more valuable than the main instruction because they prevent repeated cleanup.

Also decide what should not be automated. If quality is mostly subjective, use the model for augmentation: options, critique, structure, transformations, and first drafts. Keep human taste in the approval path. If quality is quantifiable, such as format compliance, tests passing, source coverage, or checklist completion, move more of the work into automated execution and verification.

Key takeaways

  • Start prompts with task, background information, constraints, and an explicit ask for missing context.
  • Use interviews for work where assumptions are expensive, and skip them for low-stakes transformations.
  • Ask for a blueprint before a complex deliverable so you can fix structure before polishing details.
  • Pair generation with critique from a specific opposing persona, then turn the critique into edits.
  • Verify high-stakes claims through independent checks, tools, logs, or model comparison before relying on them.
  • Convert successful prompting sessions into reusable templates with placeholders, quality checks, and gotchas.
