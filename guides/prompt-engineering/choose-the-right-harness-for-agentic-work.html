Choose the Right Harness for Agentic Work

Agentic work gets reliable when you stop treating the model as the system and start designing the harness around it: context, isolation, routing, queues, cost limits, and review gates.

Updated June 25, 2026

The Harness Is The Productive Unit

The biggest shift in agentic engineering is moving attention from prompts to the operating environment around the model. A strong model inside a messy repo, vague task, and bloated context window will still drift. A cheaper model inside a clean project, narrow interface, crisp success criteria, and deterministic workflow can often outperform it on ordinary engineering work.

Start by making the project legible to agents. Keep an orchestrator file at the root that explains the repo map, commands, quality bar, routing rules, and current mission. Pair it with a small knowledge layer: raw source notes, distilled project knowledge, and current operating instructions. This keeps agents from rediscovering the same facts every session and reduces the temptation to paste everything into context.

Good harnesses also enforce taste. Add rules that force the agent to check native platform features, standard libraries, and existing project helpers before adding dependencies or abstractions. Require a short debt note when it chooses the simple path, so future agents understand why a custom subsystem was not built. This is not just neatness. Smaller code means fewer tokens, fewer files to inspect, and less surface area for later agents to misunderstand.

Use Isolation Before Parallelism

Parallel agents are useful only when their work cannot corrupt each other. The practical unit is one task per isolated worktree, with its own branch and, when the app has state, its own branched database or local fixture set. Without isolation, parallelism turns into merge conflict management and subtle state pollution.

Use fan-out for work that benefits from independent context windows: code review, issue triage, root-cause hypotheses, design alternatives, or research synthesis. Use a tournament pattern when you need unbiased selection among options, because asking one agent to rank all its own ideas invites self-preference. Use adversarial verification when correctness matters: a separate skeptic agent should check the output against a rubric, tests, and the original task.

The failure mode is using multi-agent workflow for trivial work. Every extra agent adds context setup, token spend, coordination cost, and review burden. For a one-file bug fix, a single executor plus tests is usually better. Save dynamic patterns for tasks where context separation, independent judgment, or repeated attempts materially improve the result.

Queue Work In Phases

Long autonomous runs should not be one giant instruction. Break them into phases: research, spec, build, and review. Each phase has a different output contract. Research gathers constraints and prior art. Spec turns that into success criteria and implementation boundaries. Build executes against the plan. Review checks behavior, tests, code size, and architecture.

A task queue lets agents run unattended, but it needs hard rails. Each task should include repository scope, files likely to change, commands to run, done criteria, and what not to touch. If you want an unattended executor, the harness must explicitly remove interactive bottlenecks: no open-ended questions unless blocked, no plan mode when the plan already exists, no broad refactors unless assigned.

Durable state matters once loops run longer than a single session. Store task status, decisions, token usage, retries, and review notes outside the chat window, ideally in a database or structured local files. Treat memory as a restart checklist: who the agent is, what goal it serves, what work is assigned, what it must read, and where it records learnings. This makes overnight or multi-session work resumable instead of theatrical.

Route Models By Job, Not Prestige

Model routing is cost control and reliability control. Use a frontier model for top-level orchestration, ambiguous architecture, product judgment, and final review. Use faster or cheaper coding models for narrow execution, classification, summarization, log inspection, and repeatable loops. A high-speed model can be excellent as a sub-agent even if it struggles with complex one-shot creative builds.

Do not confuse benchmark strength with fit. A model that pushes back well against bad prompts and runs hundreds of tokens per second may be ideal for classification, adversarial checks, or small implementation tasks. The same model may fail at visual polish, 3D interaction logic, lighting, or event-heavy applications. Route design-centric UI work to the model that best handles visual judgment, and route high-volume technical work to the model that is token-efficient.

Put the router in the harness, not in your head. The root instruction file can map task classes to models: architecture review to the strongest model, bulk code edits to the efficient executor, UI refinement to the design-strong model, flaky test loops to cheap parallel workers, and final approval to a reviewer. Track cost per task, not just total bill. A dashboard or simple ledger changes behavior because expensive loops become visible.

Move Human Review To The Right Checkpoints

Human involvement is most valuable at boundaries: before coding, when requirements are still cheap to change, and after implementation, when the artifact can be inspected. Before build, use forcing questions or an adversarial pass that challenges the goal, missing constraints, and proposed design. This prevents agents from confidently implementing the wrong thing.

During execution, avoid constant interruption unless the task is risky or under-specified. The point of the harness is to let agents make bounded decisions inside a controlled lane. If every minor choice returns to the human, the workflow keeps the costs of automation without gaining throughput.

At the end, review like an engineer, not a spectator. Require tests or a stated reason they were not run. Check changed files against the intended scope. Run a skeptic pass for regressions, unnecessary abstractions, dependency creep, and unhandled edge cases. When an agent fails repeatedly, add an operating rule or eval derived from the failure. The harness should improve from corrections instead of relying on you to remember them next time.

Key takeaways

  • The model is only one part of the system. Clean context, repo structure, success criteria, and review rules often matter more than raw capability.
  • Use isolated worktrees and branched state before running agents in parallel, or parallel work will create conflicts and hidden contamination.
  • Break autonomous work into research, spec, build, and review phases so long runs stay bounded and resumable.
  • Route models by task class: strongest for orchestration and review, efficient models for narrow execution, fast models for loops and checks.
  • Constrain agents with YAGNI rules, native-first decision ladders, and dependency discipline to reduce cost and code bloat.
  • Turn repeated failures into persistent rules, evals, or skills so the harness gets better instead of repeating the same mistakes.
