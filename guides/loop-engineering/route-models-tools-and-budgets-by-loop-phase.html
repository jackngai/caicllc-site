Route Models, Tools, and Budgets by Loop Phase

Long-running agents become economical when the harness routes model strength, tool authority, and spend limits by phase instead of treating every loop iteration like a frontier-model problem.

Updated June 28, 2026

Route the Loop, Not the Prompt

The central routing mistake in autonomous coding systems is assigning one model to the whole run. A long loop is not one task. It is a sequence of different risk profiles: architectural choice, repo reconnaissance, implementation, tool execution, diagnosis, review, and final acceptance. The model that should decide the migration shape is usually not the model that should rewrite 40 similar files, and neither should be the model that polls CI every five minutes.

Build the harness around phase transitions. Each phase should declare its allowed models, tools, budget ceiling, context source, and exit criteria. A practical default is: frontier model for architecture and hard diagnosis, strong workhorse for implementation and bounded analysis, cheap or deterministic code for classification, log summarization, status polling, and bookkeeping. This is stricter than “use cheaper models when possible.” The router should know why the phase exists and what failure costs.

Treat speed as a phase property too. A very fast coding model can be valuable as a sub-agent engine for search, patch attempts, or narrow reasoning, even if it is unreliable for high-fidelity interactive builds. Conversely, a top model with expensive output tokens may be correct for the initial scaffold or migration plan, then wasteful for CSS nudges, mechanical refactors, or repeated test-fix cycles. The cost-aware system does not worship benchmark rank; it optimizes completed work per dollar under your own evals.

Define Phase Contracts

Once the loop is phase-based, every handoff needs a contract. The research phase should output structured findings, uncertainty, touched files, and proposed success criteria. The planning phase should output a task graph with dependency edges, write scopes, rollback notes, and model/tool recommendations for each node. The implementation phase should receive only the slice it owns, plus the acceptance tests it must satisfy. This prevents context bloat and avoids the common failure where one long session drifts from diagnosis into speculative rewriting.

External state is not optional for overnight loops. Store run state in Postgres, Neon, SQLite, or a durable task table rather than the chat transcript. Persist phase, model, agent role, prompt hash, repo SHA, branch/worktree, tool calls, token counts, cost, test results, approvals, and final artifacts. A loop should be resumable after process death without asking the model to reconstruct history from a compressed conversation.

Memory should behave like a restart checklist, not a diary. Role files, repo conventions, protected resources, topology, and recent lessons belong in explicit instruction files or database rows with TTLs and provenance. Do not let every observation become permanent memory. Promote only corrections that changed future behavior: “never restart container X,” “all migrations require tenant fixture tests,” “design passes need screenshot diff before completion.” Bad memory is expensive because every future phase pays for it.

Escalate on Evidence

The expensive model should enter the loop when the harness has evidence that cheaper execution is stuck, not when the task feels important. Define escalation triggers: repeated test failure with different patches, contradictory diagnostics, broad architectural ambiguity, security-sensitive tool use, or a diff whose blast radius crosses module boundaries. A workhorse model can attempt two or three bounded repair passes. If the failure signature does not change, stop spending iteration tokens and route to a frontier diagnosis phase with logs, diffs, traces, and the failed hypotheses already summarized.

The same rule applies to tool authority. Read-only analysis, grep, static checks, and test commands can be broadly available. State-changing tools need scope. SSH, deploy commands, database writes, and service restarts should be exposed through narrow wrappers with typed parameters and explicit descriptions. For unattended ops loops, require structured JSON such as `status`, `diagnosis`, `commands_requested`, `needs_approval`, `applied_fix`, and `confidence`, then branch deterministically. Human approval should gate mutation, not observation.

Parallelism also belongs behind contracts. Use isolated worktrees, branches, and database clones when agents can write code. For analysis-only agents, run quality, security, performance, and test-diagnosis passes in parallel, then merge their findings in a supervised planning phase. Avoid broad unobserved code changes from many agents against the same tree. One-agent-per-task is boring, but it reduces edit conflicts and makes spend attribution meaningful.

Budget by Role and Outcome

A useful budget is not just a monthly cap. Track spend per run, phase, role, model, success condition, and artifact. The key metric is not tokens consumed; it is cost per accepted result. Record whether the run produced a merged PR, passing tests, accepted design, resolved incident, or rejected patch. Also record output tokens separately from input and cache reads, because some agents look cheap until verbose reasoning or generated code burns the quota.

Give each role a budget envelope. The top-level planner or CEO-style agent gets a frontier allocation because bad decomposition poisons the whole run. Engineers get workhorse models by default, with escalation tickets instead of unrestricted upgrades. QA and eval agents can often run cheaper models if their job is to execute known checks, compare screenshots, inspect logs, or enforce acceptance criteria. Security diagnosis, complex tool failures, and cross-system incidents deserve stronger models because a wrong answer can cause real damage.

Subscriptions and rate limits are part of architecture. A model that is cheap on paper but rate-limited under multi-agent load may be a poor loop engine. A model with lean output behavior can stretch session limits further than one that writes heavily. Your router should expose provider quotas as runtime constraints: max parallel calls, max output tokens, retry policy, and fallback model. Do not discover at 2 a.m. that the “cheap” plan cannot sustain your worker pool.

Close the Loop With Evals

Routing only improves if the harness measures its own decisions. Run the same representative workloads across candidate model mixes: research report, migration, failing test repair, frontend/dashboard build, incident diagnosis, and review. Compare wall time, total cost, escalation frequency, human interventions, accepted output rate, and regressions introduced. Vendor benchmarks are useful hints, but your loop’s distribution is the ground truth.

Add feedback loops around repeated corrections. If agents keep closing tasks without success criteria, make success criteria mandatory in the task schema. If they pass unit tests but break visuals, add screenshot checks and route visual diagnosis to a model with stronger frontend judgment. If parallel workers collide, tighten ownership boundaries. If the frontier model is spending heavily on routine patching, move that phase back to the workhorse tier and reserve the frontier call for diagnosis summaries.

The final shape is a control system: deterministic harness outside, agentic reasoning inside, and model strength allocated where uncertainty and consequence justify it. That is how long autonomous loops stay both capable and affordable. The goal is not to find the one best model. It is to make every phase prove that it deserves the model, tools, context, and budget it consumes.

Key takeaways

  • Route by loop phase: frontier for architecture and hard diagnosis, workhorse for implementation, cheap or deterministic code for bookkeeping.
  • Persist run state outside the chat transcript, including model, role, tokens, cost, repo SHA, tool calls, tests, approvals, and outcome.
  • Escalate only on evidence such as repeated failed repair attempts, ambiguous architecture, high blast radius, or risky tool use.
  • Use isolated worktrees and cloned state for parallel writers; use analysis-only sub-agents freely when their outputs merge through a supervised planner.
  • Measure cost per accepted result, not benchmark score or raw token count.
