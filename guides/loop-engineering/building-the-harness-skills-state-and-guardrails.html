Loop Engineering

Building the Harness: Skills, State, and Guardrails

A reliable loop is not a better prompt wrapped around a model, but a harness that turns intent into scoped work, durable state, objective checks, and repeatable recovery.

Updated June 25, 2026

The Harness Is The Product

A loop becomes useful when it stops depending on the model to remember the process. The model can reason, draft, classify, and repair, but it should not be the only place where the workflow lives. Put the workflow in the harness: commands, state machines, hooks, skills, logs, databases, test runners, and review gates. The model then becomes one component inside a controlled system rather than the source of truth for what should happen next.

Start by naming the loop’s states. A software loop might be `intake`, `clarify`, `plan`, `implement`, `verify`, `review`, and `retrospect`. Each state should have a small prompt, a bounded tool set, explicit inputs, and an exit condition. Do not ask one long session to hold the whole project in context and behave well for hours. Split the work so every step can be resumed, inspected, retried, or swapped to a cheaper model.

The tradeoff is upfront friction. A state machine feels slower than asking an agent to “go build it.” But the first failed long run usually costs more than the state machine would have. The harness also gives you leverage: small models can handle classification, routing, summarization, and checklist updates, while stronger models stay reserved for high judgment implementation or review.

Skills Should Be Small And Stateful

Most teams overbuild skills. They paste broad documentation, style guides, onboarding notes, and every known convention into files that agents are expected to obey. That inflates context and makes the important instructions harder to find. A better skill is narrow, hand-curated, and biased toward gotchas: the five things the agent keeps getting wrong, the exact command that must be used, the directory that must not be touched, the migration rule that matters.

A useful skill has three parts. First, a short trigger: when this skill applies. Second, a compact procedure: what to inspect, what command to run, what output proves success. Third, a memory surface: where the loop records what it learned. That memory can be a markdown file, a database row, or a structured event log. The point is that learning survives the session instead of being trapped in chat history.

Avoid turning memory into a dumping ground. Persistent context should be edited, not appended forever. Add a retrospective step that reads execution logs and updates only durable rules: recurring failure modes, new constraints, confirmed project facts, or commands that replaced stale ones. If the agent failed because it missed a subtle repo convention, that is not “model weirdness.” It is a harness bug until the convention is captured where the next run will see it.

Proof Beats Claims

The weakest loop exit condition is “the agent says it is done.” Replace that with proof of work. For code, require test output, lint output, typecheck output, changed file lists, and relevant diffs. For UI, require screenshots or Playwright recordings. For data tasks, require row counts, checksums, sample validations, or reproducible query output. If the task matters, the loop should produce evidence that a reviewer can inspect without trusting the model’s summary.

Proof should be hard to fake accidentally. A loop can hash test logs, store command transcripts, attach screenshots, or record browser sessions. The goal is not security theater. The goal is to prevent the common failure where an agent reports that tests passed after reading old output, running the wrong command, or skipping the expensive step because context pressure nudged it toward completion.

Build verification as a separate state. The implementation agent should not grade its own work with the same loose criteria it used to create it. Verification can be deterministic commands, a second model acting as critic, external logs, or a combination. The verifier should know less about the agent’s intentions and more about the acceptance criteria. That separation catches both code defects and process defects.

Guardrails Belong In Tools

Natural language rules are helpful, but they are not enough for dangerous actions. “Never delete production data” should not live only in a prompt. Put irreversible constraints in pre-tool hooks, command allowlists, path restrictions, branch policies, and environment-level permissions. If a directory is off limits, block writes there. If a command is destructive, intercept it before execution. If a secret cannot be exposed, prevent the tool path that would reveal it.

The same applies to scope control. Long-running loops fail when they drift from a ticket into broad cleanup, dependency churn, or speculative refactors. Give each state a write boundary, a budget, and a stopping rule. A planning state can inspect widely but write nothing. An implementation state can edit selected modules. A validation state can run commands and produce evidence but should not quietly rewrite the solution unless the loop explicitly transitions back to implementation.

Parallel agents raise the stakes. Run them in isolated worktrees, sandboxes, or branched databases so they do not overwrite each other’s code or state. Parallelism is most useful for review, triage, experiments, and independent implementation slices. It is risky when multiple agents mutate shared files without ownership boundaries. The harness should make conflict difficult, not rely on agents politely staying apart.

Close The Feedback Loop

A mature loop improves after every run. Store structured events: state transitions, prompts used, model selected, tool calls, token spend, failures, retries, and final proof. Then review those events on a schedule. Look for where work stalls, where agents overrun context, which checks catch real bugs, and which instructions are ignored. The useful question is not “which model was bad?” It is “what should the harness make impossible next time?”

This is also where cost control becomes engineering rather than hand-wringing. If logs show that a flagship model is spending most of its time summarizing files, move that step to a smaller model or deterministic parser. If context bloat appears after three iterations, compress state between transitions. If validation repeatedly fails for the same reason, add a skill gotcha or a preflight check before implementation begins.

The end state is not full autonomy. It is a pipeline where humans spend attention at the highest-leverage checkpoints: defining intent, approving architecture, reviewing evidence, and deciding when a failure should change the system. The harness handles the repeatable motion. The model handles judgment inside bounded rooms. The reviewer judges artifacts, not promises.

Key takeaways

  • Treat every recurring agent failure as a harness defect to encode in rules, hooks, checks, or state.
  • Keep skills small: triggers, procedures, gotchas, and durable memory beat broad documentation dumps.
  • Use explicit states with scoped tools and objective exit conditions instead of one long autonomous session.
  • Require proof of work: logs, hashes, screenshots, recordings, checksums, and command output where appropriate.
  • Put safety rules in tooling and permissions, not only in natural language prompts.
  • Use retrospectives and observability to tune model choice, context size, validation, and cost over time.
