Run Parallel Agents Without Corrupting Code or State

Parallel agents become reliable only when each worker gets an isolated slice of code, state, context, budget, and authority, then a separate synthesis loop turns their outputs into one reviewable change.

Updated June 25, 2026

Isolation Is the Primitive

The mistake is treating parallel agents like extra terminal tabs. They are closer to concurrent writers against a shared distributed system. If they share a checkout, a database, credentials, caches, or task context, corruption is the default outcome. The harness has to make interference structurally difficult before any model starts reasoning.

Use one Git worktree per task, created from the same base commit and named by issue or experiment id. Each worktree gets its own dependency install, build cache, env file, logs directory, and port range. For applications with mutable backing state, pair each worktree with a branched database, not a shared dev database. Neon-style branch per agent, disposable Postgres schema per run, or containerized DB per worker all work. The important property is that migrations, seed data, background jobs, and destructive test fixtures cannot leak across workers.

This isolation costs disk, setup time, and orchestration code, but it buys deterministic review. A worker can be killed by deleting its worktree and database branch. A failed experiment leaves no residue. A successful one can be diffed against the common base instead of against three other agents' partial edits. If that feels heavy, reserve it for tasks with real write potential; read-only research agents can share a checkout if they cannot mutate files or state.

Quarantine Before Fan-Out

Once isolation exists, do not immediately spawn ten implementers. The next layer is task quarantine: classify the work, assign ownership, and define the exit condition before agents write code. A useful controller splits incoming work into categories such as research, implementation, verification, migration, refactor, performance, or security. Each category has a different permission set, model choice, and allowed write surface.

The quarantine prompt should force adversarial clarification: what files are likely owned, what invariants must not change, what tests prove completion, what decisions require escalation, and what would make the task unsafe to parallelize. This is where you catch hidden coupling. Two UI variants can run independently. Two agents editing the same auth middleware and migration chain cannot. One-agent-per-task is not conservative bureaucracy; it is the mechanism that prevents duplicated effort and unmergeable intent.

For large work, fan out only after quarantine creates disjoint assignments. A main orchestrator might send one agent to implement the API boundary, one to build a UI variant, one to write characterization tests, and one to audit authorization paths. The implementation agents own files. The analysis agents return reports with line references and reproduction steps. Broad unobserved edits from sub-agents should be the exception, not the default, because synthesis becomes impossible when every worker has touched everything.

Synthesis Is a Separate Job

Parallelism is useful only if the merge step is designed as a first-class phase. Do not ask the same worker that produced a patch to judge whether it should win. Model self-preference is strong, and context pollution makes it worse. Use fresh synthesis context with the original goal, the quarantine notes, the base commit, each candidate diff, test output, screenshots when relevant, and cost or latency constraints.

There are three reliable synthesis patterns. Fan-out plus select chooses one candidate and discards the rest, common for prototypes or competing implementations. Fan-out plus merge extracts compatible pieces from several worktrees, useful when workers owned separate modules. Fan-out plus adversarial verification sends the proposed final diff to skeptic agents with a rubric: requirement coverage, regression risk, security impact, migration safety, performance, and reviewability. The skeptic is not asked whether the code looks good; it is asked to find concrete reasons it fails the contract.

Keep the final change small enough for a human to review. If synthesis produces a sprawling patch, split it after the fact into stacked branches or restart with narrower quarantine. The goal is not to maximize code generated per night. The goal is to convert wall-clock time into high-confidence alternatives and evidence, then land one coherent change.

State, Memory, and Routing

Long autonomous loops need memory, but not giant chats. Treat memory as external operating state: task id, base commit, owner, allowed paths, current hypothesis, commands run, failures observed, token spend, artifacts produced, and next action. Store it in a local database, issue tracker, or structured files inside a run directory. Each heartbeat should reload this state, not the whole transcript.

This matters most when agents work overnight. Context windows fill, compaction drops details, and stale plans survive long after evidence disproves them. A disciplined research, plan, implement sequence with fresh contexts between phases is more stable than one heroic session. Research agents collect facts. Planning agents turn facts into scoped work. Implementers execute within a worktree. Verifiers run from a clean context and compare results to the original contract.

Route models by consequence, not habit. Use strong reasoning models for quarantine, architecture, synthesis, and adversarial review. Use cheaper or faster models for bounded file edits, classification, documentation sweeps, fixture generation, and repeated test reproduction. If an implementation task keeps failing, do not simply raise the model tier forever. First narrow the file ownership, improve the harness instructions, add missing tests, or give the agent a smaller theory loop. Better architecture and cleaner local rules let cheaper models succeed more often.

Budgets, Proof, and Stop Conditions

Parallel agents fail expensively when the harness has no stopping rule. Every loop needs a trigger, an action, a measurable end condition, and a budget. Budgets should include wall-clock time, token spend, number of spawned workers, number of retries, and maximum diff size. A controller should stop a worker that repeats the same failing command without a new hypothesis, touches files outside its assignment, or exceeds its review budget.

Verification should be layered. Local agents run unit tests, type checks, linters, migration dry-runs, and browser automation where applicable. Frontend changes should produce screenshots or recordings from the worker's isolated environment so the reviewer can inspect behavior without reconstructing the session. CI or an automated PR reviewer can add confidence scoring and fix suggestions, but it should not replace adversarial verification against the original requirements.

The mature posture is board-level control: humans approve goals, constraints, budgets, and final merges, while the harness manages workers, heartbeats, artifacts, and evidence. Parallel agents are not reliable because the models became obedient. They become reliable when code, state, authority, memory, and verification are partitioned well enough that each agent can be useful without being trusted with the whole system.

Key takeaways

  • Run every write-capable agent in its own worktree with isolated env, cache, ports, logs, and database branch.
  • Quarantine tasks before fan-out: classify the work, assign ownership, set permissions, and define proof of completion.
  • Separate synthesis from implementation; compare candidate diffs in a fresh context and use skeptic agents against a rubric.
  • Store loop state outside chat as structured run memory, then use fresh contexts for research, planning, implementation, and verification.
  • Route expensive models to architecture, quarantine, synthesis, and adversarial review; use cheaper models for bounded execution.
  • Stop loops by budget and evidence, not vibes: token spend, retries, touched files, diff size, and verified success criteria all need limits.
