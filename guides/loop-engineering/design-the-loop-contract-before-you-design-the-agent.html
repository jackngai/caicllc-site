Design the Loop Contract Before You Design the Agent

Long-running agents become reliable when the loop is specified as an enforceable contract, not when the prompt gets more elaborate.

Updated June 25, 2026

Start With the Contract Boundary

The core design move is to define the autonomous workflow before defining the agent that will run it. A loop contract says exactly what starts the run, what procedure may execute, what proves completion, what artifact must be produced, what memory may be written, how retries work, and where the system stops. Without that boundary, the agent is being asked to interpret intent indefinitely. That is how overnight work turns into broad refactoring, repeated test runs, and expensive self-justification.

Use a contract shape like this: `trigger`, `inputs`, `allowed tools`, `execution skill`, `verifier`, `artifact`, `memory write`, `retry policy`, `hard stop`. Keep it machine-checkable where possible. A PR trigger should pass branch, diff, issue/spec path, and CI context. A scheduled docs loop should pass yesterday's merged commits and the docs paths it owns. A performance loop should pass page routes, benchmark command, threshold, and max iterations. The agent should not infer scope from vibes when the harness can hand it bounded inputs.

The first failure mode is designing a heroic agent instead of a narrow contract. Advanced builders often make the model more capable while leaving the loop less constrained. Do the opposite. Treat the model as an executor inside a state machine. If a run cannot name its verifier and output artifact upfront, it is not ready for autonomy. Put it in training mode, require human approval at every transition, and collect enough traces to turn subjective judgment into a reviewer skill, score, or deterministic gate.

Make Execution Skill-Driven

Once the boundary is fixed, the execution phase should be a reusable procedure, not a fresh prompt assembled at runtime. Split skills from routines. The routine owns scheduling, event binding, tool access, and output destinations. The skill owns the work pattern: inspect, plan, edit, verify, summarize. This lets you improve implementation logic without editing cron, PR automation, or cloud runner configuration, and it keeps the loop's behavior stable across runs.

Resist loading a full internal encyclopedia into every agent. Large skill libraries feel thorough but increase latency, cost, and instruction conflict. Prefer a small set of curated gotchas: repository-specific test quirks, migration hazards, known flaky suites, release constraints, reviewer preferences that repeatedly matter. The agent should retrieve the few facts needed for this loop, then operate. If it needs architecture history, let it read a targeted markdown memory file or spec, not a hundred pages of standing instructions.

For complex engineering work, encode the loop as states rather than prose: `prepare`, `implement`, `verify`, `review`, `repair`, `finalize`, `retrospect`. Different models or agents can own different states, but the harness, not the model, decides transitions. An implementation agent may edit code, a verification agent may run tests and produce evidence, and a reviewer agent may compare the diff against `spec.md`. The executor can be creative inside its state, but it cannot redefine the workflow.

Verification Is the Loop's Clock

A loop iterates until verification says stop, so verification quality determines whether the system compounds progress or compounds waste. Deterministic gates are the strongest: unit tests, type checks, benchmarks, page load thresholds, lint rules, snapshot diffs, CI status, log queries with zero matching errors. For performance loops, require the agent to run the benchmark before and after, store raw numbers, and only continue if the delta is meaningful. For maintenance loops, require an exact changed-file set and a passing command list.

When the goal is partly subjective, make the judge constrained and auditable. Do not ask whether the architecture is “good.” Ask whether the patch reduces duplicate implementations, preserves public APIs, keeps modules below named dependency boundaries, and satisfies examples in the spec. Have the reviewer output a structured verdict: `pass`, `fail`, `score`, `blocking_findings`, `evidence`. Then make retry conditional on blocking findings, not on the model's desire to polish.

Require proof of work for any expensive or safety-critical loop. Store test output hashes, benchmark JSON, Playwright traces or videos, CI URLs, commit SHAs, and the exact commands run. The point is not distrust for its own sake. It is to prevent the common failure where the agent reports that it verified behavior after only reading code or after running the wrong command. If the verifier cannot produce evidence, the state machine should treat the verification step as failed.

Parallelize Inside the Contract

After the verifier is trustworthy, parallelism becomes safe because each worker has a bounded write scope and a shared definition of done. Parallel exploration is usually low risk: one agent can inspect failing tests, another can inspect relevant code paths, and another can compare recent commits. Parallel implementation requires stricter ownership. Split by module, route, package, or artifact, and tell each worker what it may change. The harness should reject or escalate overlapping writes unless the loop explicitly has an integration state.

Do not parallelize the critical path blindly. If the next decision depends on one result, do that locally or assign exactly one worker and wait. Use parallel agents for sidecar work that can finish independently: generating candidate fixes, auditing docs against a diff, checking logs across services, or preparing benchmark baselines. The loop contract should describe merge order, conflict handling, and who performs final verification. Otherwise parallelism only moves ambiguity from prompt time to integration time.

Model routing belongs here too. Cheap models can classify triggers, summarize logs, update memory, and run narrow reviewers. Stronger models should handle ambiguous implementation, cross-file design, and final spec comparison. Route by state, not by habit. A long overnight loop that uses the largest model for every log scan, file read, and retry will burn budget without improving the gate that actually matters.

Memory, Retries, and Hard Stops

Memory should make the next run shorter and less repetitive, not become a dumping ground. Write structured markdown after the loop completes: trigger context, artifact path, verifier result, failed attempts, root cause, durable gotchas, and commands that mattered. A retrospective agent can compress logs into memory, but it should be allowed to append only facts that would change future behavior. “Remember to be careful” is noise. “`pnpm test:e2e` requires the dev server on port 4173” is useful.

Retry policy is where many loops quietly become open-ended work. Define max iterations, max wall-clock time, max spend, max files changed, and escalation conditions. A good retry changes one variable at a time: apply a fix, rerun the failing verifier, inspect new evidence, then decide. If the same verifier fails twice with the same signature, the loop should stop or switch strategy. If the diff grows outside scope, stop. If the judge alternates pass and fail, stop and ask for human review.

The hard stop is not a lack of ambition. It is what lets the agent run overnight without becoming the owner of the whole project. The output artifact should be concrete: a PR, patch, benchmark report, docs update, issue comment, or failure dossier with evidence. The memory write should prepare the next loop, not extend the current one. Design the contract first, and the agent becomes replaceable infrastructure inside it. Skip the contract, and the agent becomes an expensive process with permission to reinterpret the job forever.

Key takeaways

  • Define every loop as `trigger`, `procedure`, `verifier`, `artifact`, `memory`, `retry`, and `hard stop` before choosing the agent.
  • Use state machines and code-based gates for completion; natural language instructions are not reliable control flow.
  • Prefer deterministic verification, and make subjective judges structured, constrained, and evidence-producing.
  • Keep skills small and curated around durable gotchas instead of loading broad documentation into every run.
  • Parallelize only where ownership, write scope, merge order, and final verification are explicit.
  • Control cost with state-based model routing, iteration limits, wall-clock limits, and stop conditions tied to verifier evidence.
