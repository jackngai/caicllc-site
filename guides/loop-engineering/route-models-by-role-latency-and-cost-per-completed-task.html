Route Models by Role, Latency, and Cost per Completed Task

The best routing table is not a model preference chart, but a control system that minimizes cost per verified completion while reserving scarce reasoning for the steps where failure is expensive.

Updated June 25, 2026

Route Around Failure Cost

A mature loop should not ask, "Which model is best?" It should ask, "Which model is cheapest after retries, reviews, quarantines, and failed overnight runs are counted?" Raw token price is a weak proxy. The unit that matters is cost per completed task, where completion means the harness produced the intended artifact, passed verification, left an inspectable trail, and did not require a human to rescue the run.

Build the routing table from failure cost, not task labels alone. Frontier models belong where a wrong answer poisons the whole trajectory: architecture selection, decomposition, threat scanning of untrusted input, migration strategy, ambiguous bug diagnosis, and final acceptance reasoning. Fast workhorse models belong where errors are local and cheap to catch: boilerplate edits, narrow refactors, fixture generation, classification, log summarization, first-pass review, and bounded sub-agent analysis. A 300 tokens per second coding model can be valuable even if it misses details in complex interactive builds, provided the harness uses it as a high-throughput worker rather than the source of architectural truth.

A useful first table has four columns: role, allowed models, promotion trigger, and verification gate. For example: `planner = frontier/high effort`, `implementer = workhorse/medium`, `classifier = small/fast`, `security scanner = frontier`, `reviewer = workhorse plus escalation on uncertainty`, `final judge = frontier only when diff risk is high`. The promotion trigger is the important part. Escalate on repeated test failure, large blast radius, security-sensitive files, novel framework usage, conflicting requirements, or low confidence from multiple reviewers. Do not escalate because the agent is verbose or indecisive. Escalate because the next mistake is costly.

Put Routing Inside the Harness

Once routing is framed by failure cost, the next mistake is leaving it to prompts. Put the policy in the harness so every loop executes the same state machine: ingest, classify, plan, allocate, run, verify, compress, route again. The agent can reason inside a step, but the harness should own phase boundaries, model selection, retry budgets, and stop conditions. This prevents the common long-loop failure where a strong model burns context and budget reinterpreting its own stale conversation.

Keep phase state outside the chat transcript. Store task id, branch, model, prompt hash, token counts, tool calls, test results, reviewer verdicts, and final artifacts in Postgres, SQLite, or another durable store. Treat memory as a restart checklist, not a diary: who the agent is, what goal it owns, what files or issues are in scope, what has already failed, what criteria must pass, and where to write learnings. Then start fresh contexts between research, plan, and implementation when the phase changes. Compression is a lossy operation; external state gives you resumability without making the next model inherit every exploratory wrong turn.

The router should also be allowed to say no. External inputs such as email, tickets, comments, and web pages should pass through a hardened inspection lane before any tool-using agent sees them. Use the strongest reasoning model for first-pass prompt-injection and exfiltration detection, with non-LLM controls in front: spam filters, allowlists, token caps, attachment limits, and quarantine. This is not conservative overkill. A cheap classifier that obeys an injected instruction can convert a low-cost path into a credential leak or denial-of-wallet event.

Parallelize With Bounded Roles

After the harness owns routing, parallelism becomes a scheduling problem rather than a prompt trick. Use isolated worktrees, branches, containers, and branched databases so agents can run without trampling each other. One-agent-per-task is still the default for write access. Broad codebase sweeps can fan out aggressively, but the write set must be partitioned by file, module, or issue. If ownership cannot be made explicit, route sub-agents to analysis-only mode and let a supervised implementation agent apply the changes.

The practical pattern is `frontier planner -> many cheap bounded workers -> independent reviewers -> frontier arbiter only on conflict`. Workers can run fast models for file-by-file migrations, test additions, docs sweeps, lint fixes, and mechanical API updates. Reviewers can be cheaper models assigned different lenses: correctness, security, performance, and maintainability. The arbiter should not reread everything by default. Feed it structured deltas: changed files, failing checks, reviewer disagreements, confidence scores, and minimal patches. Spend frontier tokens where compression has already reduced the decision surface.

Watch for correlated failure. Ten cheap agents given the same vague instruction will often make ten compatible-looking mistakes. Diversity helps: vary prompts by role, route one reviewer to a different model family when possible, and require concrete evidence in review outputs such as failing command, file path, line, invariant, or reproduction step. For large migrations, sample deeply before scaling. Run three files end to end through the full loop, measure defect rate and review burden, then fan out. Parallelism multiplies both throughput and bad assumptions.

Measure Effective Model Value

The routing table should evolve from logs, not brand loyalty. For each route, track wall time, input tokens, output tokens, cache reads, retries, failed tool calls, test failures, human interventions, reverted patches, and post-merge defects. Then compute by task class: median cost per verified completion, p90 wall time, retry rate, escalation rate, and defect escape rate. A cheaper model that needs three retries and a frontier rescue is not cheaper. A more expensive model that produces dense, correct architecture in one pass may be the bargain for planning.

Use effort levels as part of routing. High or max effort is justified for initial architecture, complex front-end composition, design-system extraction, hard debugging, and security reasoning. Medium effort is usually enough for iterative implementation after the plan is fixed. Low effort or smaller models fit copy swaps, CSS nits, classification, issue triage, and fixture generation. This is especially important in UI loops: the first scaffold may need a strong design model to establish layout, interaction, and responsive structure, while later tweaks should not pay the same reasoning tax.

Budget controls need to fire before the model call, not after the invoice. Enforce per-task token ceilings, per-run spend caps, max parallel workers, max retries, and model allowlists by repository, team, and risk tier. Add denial-of-wallet guards for untrusted payloads: truncate, summarize with a scanner, or quarantine before full processing. When the loop hits a cap, it should produce a useful checkpoint: current state, best hypothesis, failing gate, and the exact decision needed. A stopped loop with clean state is cheaper than a wandering loop with hidden partial work.

Make the Table Operational

The final table should be small enough to audit and strict enough to matter. Do not expose "use best model" as a general option. Define lanes: `intake`, `planner`, `implementer`, `subagent-analysis`, `subagent-write`, `review`, `security`, `debug-escalation`, `final-acceptance`. For each lane, specify model candidates, context budget, tool permissions, write permissions, retry count, verification command, and escalation rule. Store it in the repo beside agent rules and skills so the project stays portable across coding agents and vendors.

A concrete default: frontier for intake security, architecture, hard debugging, and final judgment on high-risk diffs; workhorse coding models for implementation and repeated edit loops; fast reasoning models for bounded sub-agents and classification; smaller models for summaries and routing metadata. Promote only on evidence: failing tests after bounded retries, high-risk files, reviewer disagreement, suspected injection, or unclear success criteria. Demote as soon as the task becomes mechanical.

This is the central discipline of model routing: spend scarce reasoning on irreversible decisions and hostile surfaces, then let cheaper agents do the repeatable work under verification. The loop becomes more autonomous not because every step is smarter, but because the system knows which mistakes matter, catches the cheap ones automatically, and pays for frontier judgment only when it changes the outcome.

Key takeaways

  • Optimize for cost per verified completion, not token price or benchmark rank.
  • Put model routing in the harness with promotion triggers, verification gates, and durable external state.
  • Reserve frontier models for architecture, hard debugging, security scanning, and high-risk acceptance decisions.
  • Use cheaper or faster models for bounded implementation, classification, summaries, and parallel sub-agent work.
  • Parallelize only with explicit ownership, isolated environments, and review paths that catch correlated failure.
  • Enforce token, retry, rate, and spend caps before model execution, especially on untrusted inputs.
