Make Verification a Gate, Not a Suggestion

Long-running agents only become trustworthy when completion is defined by external evidence, enforced gates, and explicit boundaries for human judgment.

Updated June 28, 2026

Stop Accepting Narrative Completion

The failure mode of advanced agent loops is rarely that the model cannot write code. It is that the loop accepts the wrong termination signal. If the agent can mark a task done because it says tests passed, reviewed the diff, or inspected the UI, the harness has delegated quality control to the same system being evaluated. For overnight work, that is not automation. It is unattended self-certification.

Treat every autonomous workflow as a state machine whose transitions require artifacts, not prose. Planning can transition to implementation only after a spec exists with acceptance criteria, affected surfaces, non-goals, and validation zones. Implementation can transition to verification only after changed files, commands run, and environment assumptions are captured. Verification can transition to done only after deterministic gates produce machine-checkable outputs: exit codes, logs, screenshots, videos, coverage deltas, hashes, CI statuses, or reviewer verdicts.

The practical shift is small but strict: the agent may propose that work is complete, but the harness decides. Completion becomes a predicate over evidence. A good predicate is boring: `lint == 0`, `typecheck == 0`, `unit == 0`, `e2e == 0`, `browser_artifact.exists`, `reviewer.blockers == []`, `human_zone.approved == true` where required. The more autonomous the loop, the less room you leave for interpretive language.

Build the Spec as the First Gate

Once completion is externalized, the first gate has to be the spec. Advanced builders often skip this because they already know the goal, but agents need the goal decomposed into verifiable buckets. The spec should not be a long product brief. It should be an executable contract for the loop: task class, risk tier, files likely involved, acceptance checks, rollback constraints, human validation zones, and proof artifacts expected at the end.

Use an interview phase when ambiguity remains, but do not let it become conversational drift. The agent should ask only for constraints that change implementation or verification. For example: which payment paths are out of bounds, which browser states must be captured, which generated files are allowed, which APIs cannot be touched, which visual deltas require a human taste call. The result should be compact enough to stay in context and explicit enough that a second agent can verify against it without asking what was intended.

For long loops, split the spec into checkpoints rather than one monolithic finish line. A migration might gate on schema diff, generated client update, unit tests, integration tests, and rollback notes. A frontend change might gate on DOM assertions, Playwright screenshots at fixed viewports, interaction video, and a human approval flag for visual judgment. The key is to separate objective evidence from subjective acceptance before the agent starts editing.

Make Verification Multi-Layered

A single verifier is too easy to satisfy accidentally. The stronger pattern is layered verification, where each layer catches a different class of false success. Local deterministic checks catch syntax and contract breaks. Browser automation catches UI states the model would otherwise describe from memory. CI catches environment skew. Adversarial review catches reasoning holes, missing tests, and spec violations. Human validation zones catch taste, money movement, security posture, irreversible data changes, and other areas where objective checks are necessary but insufficient.

Proof of work matters because agents can summarize actions they did not actually perform, especially in long contexts. Require artifacts that are expensive to fake inside the workflow: raw command logs, test output digests, Playwright traces, screenshots, GIFs, coverage reports, migration dry-run output, exact commit SHAs, and hashes of generated reports. A harness can store these under a run directory and require the verifier to reference filenames instead of accepting a free-form claim.

Adversarial reviewers should run in separate context windows or worktrees. Do not ask the implementer to critique itself. Give the reviewer the spec, diff, artifacts, and a rubric, then require a structured verdict: blockers, risks, missing evidence, and suggested next gates. For large audits, fan out reviewers by subsystem, then synthesize only evidence-backed findings with file and line references. For design or diagram work, render the artifact and inspect pixels or screenshots before critique. The principle is the same: externalize perception.

Use Parallelism Without Losing Control

Parallel agents are useful only when the harness prevents them from turning into parallel uncertainty. Use worktrees for independent implementation attempts, research branches, or isolated reproduction loops. Use fan-out when the task naturally decomposes by subsystem or hypothesis. Use tournament-style comparison when choosing among competing implementations, but compare in isolated contexts so one option does not anchor the evaluator.

The control plane should classify work before spawning agents. Low-risk tasks can enter auto mode with lint, typecheck, and focused tests. Medium-risk tasks need implementation plus independent verification. High-risk tasks require pre-tool hooks, restricted write scopes, and human approval gates. Some commands should be blocked at the tool layer regardless of prompt content: destructive git operations, production credential access, edits to payment or auth directories without an approved spec, or migrations without a dry-run artifact.

Loop-until-done is most valuable when the success condition is crisp: reproduce a flaky test, eliminate a type error, make a Playwright scenario pass, resolve every reviewer blocker. It is wasteful when quality is mostly taste. In those cases, automate variant generation and evidence capture, then route the choice to a human. This avoids the common failure where an agent spends tokens optimizing a subjective surface and leaves behind operational debt disguised as polish.

Keep Memory Small and Operational

Persistent memory should improve future gates, not become a junk drawer. Large auto-generated skill libraries often degrade performance because they add vague instructions and stale context. Prefer a small set of curated gotchas: repo-specific commands, flaky test notes, forbidden patterns, architectural invariants, known browser setup issues, release hazards, and examples of past verifier failures.

After each substantial run, a retrospective agent can inspect logs and propose memory updates, but it should not write them blindly. Treat every agent failure as a harness bug: missing gate, weak artifact requirement, unsafe permission, unclear spec field, bad routing, or excessive context. The fix should be structural. Add a pre-tool hook, tighten the state transition, add a new proof artifact, narrow a skill, or introduce a human zone. Avoid compensating with longer reminders.

Cost control follows from this architecture. Route cheap models to classification, log summarization, artifact indexing, and simple checks. Use stronger models for spec formation, implementation in unfamiliar areas, and adversarial review. Batch large scans and spawn agents only when prerequisites are met. Most importantly, stop loops at gates, not at token exhaustion. An autonomous agent that cannot produce the required evidence is not almost done. It is blocked, and the harness should say exactly where.

Key takeaways

  • Define done as a predicate over artifacts, exit codes, reviewer verdicts, and approvals, not as an agent message.
  • Write a compact implementation spec before edits begin, with acceptance checks, risk tier, write scope, and human validation zones.
  • Require proof-of-work artifacts such as logs, hashes, traces, screenshots, videos, CI results, and exact changed-file inventories.
  • Run adversarial reviewers in isolated contexts and make them verify against the spec and artifacts, not the implementer’s summary.
  • Use parallel agents for decomposable work, but route by risk and enforce write scopes, hooks, and deterministic stop conditions.
  • Keep persistent memory small: curated gotchas and harness fixes beat large prompt libraries.
