Design the Minimal Autonomous Loop

Autonomy works when the loop is small enough to inspect: one trigger, one bounded skill, one verifier, one artifact, and one memory write, repeated only for workflows whose success can be measured.

Updated June 28, 2026

Start With The Loop You Can Kill

The minimal autonomous loop is not a prompt that keeps running. It is a control system with a narrow contract: a trigger creates work, a skill performs bounded execution, a verifier decides whether the result is acceptable, an artifact records the outcome, and memory updates the next run. If any one of those parts is vague, the agent will spend tokens converting ambiguity into motion.

Begin by defining the kill condition before the work. For a performance loop, that might be `p95_page_load_ms < 50` across a fixed route list, measured three times with warm caches disabled. For a CI repair loop, it is green tests on the target branch plus no unrelated diff. For documentation sync, it might be a reviewer score threshold against yesterday's merged code, but that is already less reliable because the verifier is judging semantic coverage rather than measuring an external fact.

This is why the smallest loop is usually the most useful loop. Do not start with “improve the codebase overnight.” Start with “on every PR, run the failing test subset, patch only files implicated by the failure, rerun, and stop after green or three attempts.” The smaller the loop, the easier it is to set budgets, detect drift, reproduce failures, and decide whether autonomy earned its keep.

Bind Execution To A Skill

Once the stop condition exists, the execution phase needs to be boring. Put the working procedure in a reusable skill file, not in the scheduler or trigger. The trigger should say when to run and with what inputs. The skill should say how to inspect, edit, test, and report. Keeping those separate lets you tune the agent's behavior without touching cron, PR automation, or remote routine configuration.

A good skill is not a motivational prompt. It is an operational runbook: allowed directories, forbidden changes, commands to prefer, command timeouts, diff discipline, expected artifact paths, and recovery behavior when tools fail. For a refactor loop, the skill might require reading `spec.md`, generating a file-level plan, editing only one module per iteration, running typecheck and targeted tests, then asking a reviewer skill for pass/fail against simplicity, duplication, and API compatibility constraints.

Bound the skill aggressively. Give it a working set, a maximum number of attempts, and a definition of “no progress.” If the same test fails twice with the same stack trace, require the loop to write a blocked artifact instead of trying adjacent guesses. If the agent touches files outside its scope, fail verification. These constraints are not bureaucracy; they are how you keep a long-running loop from becoming an expensive random walk.

Make Verification The Center

The verifier is the real product. Deterministic checks are best: unit tests, benchmarks, lint, typecheck, snapshot diff thresholds, migration dry-runs, log-query counts, uptime probes, bundle size budgets. They give the loop a clean boolean or numeric gradient, which means the agent can compare attempts and decide whether it is moving toward the goal.

When the goal is not deterministic, use judgment only after narrowing the surface. LLM-as-judge can work for architecture cleanup, documentation quality, or spec parity, but it needs a rubric that produces a score or binary result and cites concrete failures. “Does this feel good?” is useless. “Does the implementation preserve public APIs, reduce duplicate branches below N, keep changed files under M, and satisfy every requirement in `spec.md`?” is at least auditable.

Treat judged loops as higher risk and higher cost. Add human checkpoints in training mode until the loop has a history of correct decisions. During training, pause after planning, after first diff, and before writeback. Promote the loop only when its artifacts show stable behavior: small diffs, correct test selection, low retry counts, and useful blocked reports. The goal is not to remove humans everywhere; it is to spend human review on the few decisions that still need taste or authority.

Persist Memory, Not Chatter

A loop that starts from scratch every time pays twice: once in tokens, once in repeated mistakes. Persist compact memory in markdown or another inspectable store. Keep it separate from the output artifact. The artifact says what happened in this run. Memory says what the next run should know: known flaky tests, benchmark baselines, previous failed hypotheses, approved conventions, changed thresholds, and links to prior artifacts.

Memory should be appendable but curated. If the agent writes a transcript, the next run will waste context reading noise. Use a fixed schema: date, trigger, goal, inputs, verifier result, diff summary, commands run, failure signatures, decisions to preserve, and next suggested action. For long overnight loops, add a rolling summary file that compresses prior runs into facts under headings the skill knows how to read.

Parallelism belongs around this memory boundary. Run independent inspectors in parallel: one agent profiles performance, one searches logs, one checks documentation drift, one reviews test failures. Do not let multiple workers write the same files or the same memory section. Fan out for evidence, then fan in through a single coordinator that chooses the next bounded execution step. Parallel agents amplify throughput only when their ownership boundaries are explicit.

Route Models And Costs By Risk

Autonomy fails economically before it fails technically. A loop that can run for hours needs hard budgets: maximum iterations, maximum wall time, maximum changed files, maximum tool calls, maximum tokens, and a rule for escalating when the verifier does not improve. Non-deterministic verification deserves stricter caps because the agent can chase evaluator noise forever.

Route models by phase. Use cheaper models for classification, file triage, log clustering, summarizing prior artifacts, and generating candidate hypotheses. Use stronger models for plan selection, cross-file edits, verifier interpretation, and final blocked reports. If the loop supports local and cloud execution, choose based on dependencies: local routines are better when the skill needs system binaries, private files, or repo-specific tooling; remote routines work only when dependencies and skills are available through the repository or APIs.

The final autonomy decision is ruthless: if the workflow is not repeated, tool-accessible, and verifiable, do not loop it. Keep it as an assisted session or training-mode routine. The frontier pattern is not bigger agents with looser instructions. It is smaller loops with stronger contracts, better verifiers, cheaper routing, and memory that lets each run begin where the last one stopped. Build the minimal loop first; only then decide whether it deserves the night.

Key takeaways

  • A reliable loop has five inspectable parts: trigger, bounded skill, verifier, artifact, and memory write.
  • Autonomy is earned by objective verification, not by longer prompts or broader instructions.
  • Keep skills separate from triggers so execution logic can improve without changing scheduling or event wiring.
  • Use training mode and human checkpoints for new or judged workflows before allowing unattended runs.
  • Parallelize evidence gathering, but serialize writes to code, artifacts, and memory.
  • Set iteration, time, token, file-change, and verifier-improvement budgets before any overnight loop runs.
