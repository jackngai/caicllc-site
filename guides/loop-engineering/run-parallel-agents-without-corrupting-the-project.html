Run Parallel Agents Without Corrupting the Project

Parallel agents only increase throughput when every task has an isolated workspace, isolated state, explicit ownership, and an inspectable path back to one merged decision.

Updated June 28, 2026

Isolation Is The Throughput Primitive

The central rule is simple: never scale agents by letting them share mutable project state. Scale them by cloning the decision surface. Each agent should get its own Git worktree, branch, dependency cache, env file, and database branch or disposable schema. If the project has queues, object storage, search indexes, or external APIs, the harness should provide per-task namespaces and fake credentials by default. Shared state is allowed only for read-only artifacts: docs, fixtures, baseline traces, and task specs.

A practical launcher should create the worktree, install or hydrate dependencies, provision a database branch, write a task-local `.env`, record the base commit, and attach a budget before the model sees the prompt. The agent should not improvise this setup. Deterministic bootstrap beats clever prompting because it makes failures attributable: bad migration, flaky test, insufficient prompt, or model error. When an overnight run fails, you need a run directory with logs, diffs, screenshots, token spend, test output, and the exact base SHA, not a transcript archaeology project.

The failure mode is partial isolation. Two agents on separate branches but the same dev database will corrupt each other's conclusions. Two agents with separate databases but the same Redis namespace will chase phantom jobs. Two agents with separate worktrees but one shared browser profile will make visual tests non-reproducible. Treat state like code: branch it, name it, clean it, and make teardown part of the harness contract.

Ownership Beats Coordination

Once isolation exists, the next constraint is task ownership. One agent owns one task, and a task has a write boundary. That boundary can be a package, feature slice, failing test, migration, or research question, but it must be stated before launch. A useful task file includes the goal, non-goals, allowed paths, commands to run, success criteria, expected artifacts, and the handoff format. If two agents need to edit the same files, that is not parallel implementation. It is a design problem waiting to become a merge conflict.

Use short contexts for the phases that should stay clean. A common pattern is research, plan, implement, verify, with context resets between phases. Research agents can run in parallel and return findings with file and line references. The planner synthesizes those findings into bounded implementation tickets. Implementation agents then operate with narrower context and less room for goal drift. This is slower than telling ten agents to “fix auth,” but it produces artifacts a human or reviewer agent can inspect.

Do not give broad write access to sub-agents by default. Let analysis agents read, classify, and rank. Let implementation agents change only their assigned surface. Let QA agents verify without patching unless the workflow explicitly routes them into a fix pass. The point is not hierarchy theater. It is preserving accountability: when a regression appears, you should know which task introduced it and which reviewer missed it.

Fan Out, Then Synthesize

Parallelism is strongest when agents are exploring independent possibilities, not when they are all trying to be the final author. For design choices, bug theories, API approaches, or performance plans, fan out several agents in separate contexts with the same rubric and ask for concrete evidence. Then run a synthesis pass that compares claims against the repository, not against vibes. The synthesizer should produce a decision record: selected approach, rejected alternatives, evidence, risks, and the implementation ticket that follows.

For high-stakes choices, use tournament review instead of list scoring. Pair options head to head in isolated comparisons, advance winners, then run a skeptic pass against the final pick. This reduces self-preference and the tendency for a model to rationalize whatever appears most recently in context. The skeptic should not ask “is this good?” It should check the decision against a rubric: correctness, blast radius, testability, migration safety, rollback path, observability, and cost.

The same pattern works for code review. Have implementation agents produce diffs, then have independent reviewers evaluate them without seeing the agent's self-summary first. A QA agent runs tests and browser automation. A security or data-integrity agent checks the changed surface. A synthesizer merges the review output into a small set of required fixes. Only after that should a human review the final branch. Human attention is scarce, so spend it on the compressed decision trail, not raw agent chatter.

Make Verification A Loop, Not A Hope

Long autonomous runs fail when “done” means the agent decided to stop. Replace that with a verification loop driven by executable checks and bounded retries. The task spec should define the stop condition: tests pass, benchmark under threshold, screenshot diff accepted, migration round-trip verified, linter clean, or reproduction script no longer fails. If the check fails, the harness feeds back only the relevant failure output and gives the agent another attempt within a fixed retry and budget envelope.

Verification should be multimodal when the surface is multimodal. Frontend agents should capture screenshots or GIFs, compare key viewports, and attach artifacts to the PR. Backend agents should run contract tests, migration tests, seed-data checks, and relevant benchmarks. Debugging agents should preserve reproduction commands. Performance agents should record before and after numbers with hardware, dataset, and command line. A claim without an artifact should not survive synthesis.

Keep the loop narrow. A loop that can edit the whole repository after every failure will eventually create accidental scope. Prefer a controller that classifies the failure, routes it back to the owning task, and stops when the issue crosses ownership boundaries. Some failures should create a new task rather than expand the current one. That is how overnight work stays inspectable in the morning.

Route Models And Budgets Like Infrastructure

Model choice belongs in the harness, not in each agent's improvisation. Use stronger reasoning models for architecture, synthesis, adversarial review, and ambiguous debugging. Use cheaper or faster models for classification, fixture generation, routine edits, documentation sweeps, and narrow analysis. If an implementation task is well specified and the codebase is clean, a cheaper model should often succeed because the harness is carrying the complexity.

Track spend per task, per phase, and per artifact. Token totals alone are not enough. You want cost per merged change, cost per accepted finding, retry count, review rejection rate, and the commands that dominate wall time. Batching also matters: queue agents behind prerequisites instead of spawning every possible worker immediately. A fan-out of twenty agents that all rediscover the same missing migration is not parallelism. It is unpriced confusion.

Memory should be external and curated. Store mission, repo rules, task history, recurring corrections, and known failure modes in files or a database the launcher injects deliberately. Do not rely on one giant conversation to remember the project. Heartbeat-style context works better: who the agent is, what task it owns, what rules apply, what artifacts to read, and where to write learnings. Parallel agents become safe when the project is not a shared terminal session but a controlled factory of isolated attempts, verified artifacts, adversarial review, and deliberate synthesis. That is the difference between ten agents creating ten messes and ten agents producing one inspectable result.

Key takeaways

  • Use one worktree, branch, database namespace, env file, and run directory per agent task.
  • Assign one agent to one owned task with explicit write boundaries and success criteria.
  • Fan out for exploration, then synthesize into a decision record before implementation.
  • Run tournament and skeptic reviews in fresh contexts to reduce self-preference and weak consensus.
  • Make completion depend on executable verification artifacts, not the agent's own confidence.
  • Route models and budgets per phase so expensive reasoning is reserved for decisions that need it.
