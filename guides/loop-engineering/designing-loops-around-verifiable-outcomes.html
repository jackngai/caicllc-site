Loop Engineering

Designing Loops Around Verifiable Outcomes

A reliable agent loop starts with a verifiable contract: what starts it, what it is allowed to do, how success is checked, and what evidence it leaves behind.

Updated June 25, 2026

Start With The Loop Contract

A loop is not a longer prompt. It is a recurring work system with a contract. Before any agent runs, write down four things: the trigger, the execution path, the success check, and the recorded output. If one of those is vague, the loop will turn into an expensive chat session that keeps improvising.

The best first candidates are boring, repeated tasks with objective success conditions. Performance optimization is a clean example: trigger the loop from a human command, have the agent measure page load time, make bounded changes, rerun the benchmark, and stop only when every target page is under a defined threshold. Test repair, documentation sync, log triage, and regression cleanup can work for the same reason. The loop has something concrete to observe.

Do not start with subjective generation unless you have a measurement strategy. “Improve our docs” is too soft. “Compare docs against yesterday’s merged changes, open a diff, and pass a reviewer check for missing public API behavior” is closer to a loop. The move is to translate the desire into an observable end state before automation begins.

Define The Trigger Precisely

The trigger decides when the loop is allowed to spend time, tokens, and system access. Common triggers include a manual command, a pull request event, a cron schedule, a production log alert, or a nightly maintenance window. Each one has a different risk profile. A manual trigger is easiest to debug. A scheduled loop is useful for recurring cleanup. An event-driven loop can be powerful, but it needs tighter guardrails because it can run when nobody is watching.

A good trigger includes context, scope, and budget. For example: “Every weekday at 2 a.m., inspect the prior day’s merged code changes, update affected markdown docs, run the docs consistency reviewer, and open a pull request if changes are needed.” That is much safer than “sync docs nightly.” The agent knows what period to inspect, what artifacts it may change, what check to run, and what output to produce.

For new workflows, use a training mode. The loop still follows the intended path, but it pauses for approval at each step: collect context, propose the execution plan, make the first change, run verification, record output. Once the logic is boring and repeatable, remove approvals selectively. This prevents you from automating uncertainty.

Make Execution Skill-Driven

The execution path should be a reusable procedure, not fresh instructions invented each run. Put the work instructions in a skill or routine file: how to inspect the repo, what tools to use, what files are in scope, what style rules apply, how to run tests, and how to report uncertainty. Then the loop calls that procedure each time.

This separation matters because scheduling and logic age differently. The trigger might remain stable for months while the execution skill improves every week. Keeping them separate lets you refine the agent’s behavior without rewriting the automation that starts it. It also reduces drift. A loop that repeatedly calls the same tested skill is easier to reason about than a loop that depends on a new prompt assembled at runtime.

Complex work should be broken into specialized roles only when the boundary is real. A planner, implementer, and validator can be useful if they pass structured state between them, such as a markdown plan, changed file list, benchmark table, or review verdict. Do not split work just to look sophisticated. Each added agent increases coordination cost and creates another place for state to go stale.

Use Verifiers, Not Hope

The success check is the center of the loop. Deterministic checks are strongest: unit tests pass, CI is green, benchmark latency is below 50 ms, lint has no errors, coverage does not drop, or a numerical quality score clears a threshold. These checks give the loop a stop condition that does not depend on mood or persuasion.

Some useful goals are not fully deterministic. Architecture cleanup, documentation quality, or spec parity may need a reviewer skill or LLM-as-judge. Treat that as a weaker verifier, not a magic replacement for tests. Give the reviewer concrete criteria: binary pass/fail where possible, specific scoring dimensions, examples of unacceptable output, and a requirement to cite evidence from the changed files or spec. A judged goal should still produce a decision the loop can act on.

The common failure mode is an agent that keeps iterating because “better” has no ceiling. Prevent that with hard limits: maximum iterations, maximum runtime, maximum token spend, and escalation rules. If the loop cannot pass verification after the limit, it should stop, record what failed, and hand a compact report to a human. A failed loop with evidence is useful. An infinite loop with confidence is not.

Record Output As Memory

Every loop should leave behind a durable record: what triggered it, what it read, what it changed, which checks ran, what passed, what failed, and what decision was made. A simple markdown file is often enough. The point is not ceremony. The point is to prevent the next iteration from rediscovering the same facts and repeating the same mistakes.

This memory should be structured enough to compare runs. For a performance loop, store benchmark numbers before and after, changed files, and remaining slow pages. For a documentation loop, store merged commits inspected, docs touched, reviewer verdict, and unresolved gaps. For a log-sweeping loop, store error signatures, frequency, suspected cause, linked PR, and whether the error disappeared after deployment.

Memory also enables second-order loops. One loop can optimize code and record metrics. Another can scan those records weekly and identify regressions, flaky checks, or expensive tasks that should be narrowed. Without recorded output, each run is isolated. With recorded output, the system can improve its own operating procedure.

Design For Cost And Containment

Autonomous loops can run for hours if their goal is broad or their verifier is fuzzy. Cost control is an engineering requirement, not an afterthought. Start with narrow scope, cheap checks, and local routines where dependencies are available. Move to remote or scheduled execution only after the loop’s behavior is proven.

Prefer loops that refine existing systems before asking agents to build large new features from scratch. Maintenance, optimization, refactoring under tests, PR cleanup, and documentation alignment fit the loop model because the agent can observe a current state, make a bounded change, and verify the result. Greenfield work often lacks stable checks, which makes the loop wander.

The practical test is simple: can you write the loop contract on one page and point to the exact artifact that proves completion? If not, keep designing. Define the trigger more tightly, turn the execution into a skill, build a reviewer or deterministic check, and decide what memory should be written. The loop begins before the agent runs.

Key takeaways

  • Model every loop as a trigger, execution path, success check, and recorded output.
  • Choose repeated work with objective verification before automating subjective workflows.
  • Keep execution logic in reusable skills or routines so behavior improves without changing the trigger.
  • Use reviewer skills only when deterministic checks are not enough, and require clear pass/fail or scored evidence.
  • Set iteration, runtime, and token limits so failed loops stop with useful diagnostics.
  • Write durable loop memory so later runs can compare results instead of rediscovering context.
