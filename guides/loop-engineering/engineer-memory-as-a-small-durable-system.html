Engineer Memory as a Small, Durable System

Long-running agents do not need more context; they need a small memory system that decides what survives, when it is read, and how it is proven current.

Updated June 25, 2026

Treat Memory as Runtime State

The central mistake in long autonomous loops is treating memory as a larger prompt. A prompt is an instruction payload. Memory is runtime state. If you let every transcript, plan, tool result, preference, and failure note accumulate in context, the agent becomes slower, more expensive, and less accurate because old intent competes with current evidence. The better pattern is a small durable system: a few markdown checkpoints for human-readable continuity, append-only retrospective logs for learning, scoped gotcha files for repeated hazards, and structured workflow state in SQL or a vector store when retrieval needs to be selective.

Start by separating memory by read frequency and authority. The heartbeat file is read every loop and should be tiny: identity, current goal, assigned issue, definition of done, files to inspect first, budget, and where to write results. The checkpoint file is read on resume and after compaction: current decision tree, accepted constraints, rejected approaches, and next action. Retrospectives are not read by default. They are mined by a maintainer loop that promotes only recurring failures into gotchas or harness rules. This promotion step is where memory becomes engineering rather than journaling.

Make Checkpoints Replace Context Dumps

Once memory has tiers, the first practical design choice is to make checkpoints the only durable narrative the agent is allowed to trust. A checkpoint should be rewritten, not appended, at loop boundaries. It answers: what are we building, what has already been proven, what is still uncertain, what changed since the last pass, and what would make the next pass stop. Keep it short enough that a fresh agent can read it before touching the repo. If it cannot fit in a few hundred lines, it is no longer a checkpoint; it is an unindexed archive.

The failure mode is stale baggage. Agents often preserve an early assumption because it was stated confidently in a prior session, even after the code or tests disprove it. Fix that with explicit evidence fields. For each important decision, store the source: test name, commit, file path, issue comment, benchmark, screenshot, or log hash. For claims that expire, add a timestamp or invalidation condition. A good checkpoint says, “API pagination is cursor-based, verified in integration test X,” not “pagination is handled.” The former lets a resumed agent reason from evidence; the latter becomes folklore.

Promote Logs Into Gotchas

After checkpoints carry the active story, retrospectives become the training data for the harness. Every completed loop should write a compact execution record: task id, model, tools used, wall time, token cost, files touched, gates passed, gates failed, human interventions, and the final reason the loop stopped. Failed loops should add the smallest reproducible description of the miss: skipped migration, hallucinated CLI flag, edited generated files, ignored visual regression, exceeded budget, or claimed tests ran without evidence.

Do not feed this entire history back into the agent. Run a retrospective pass that clusters repeated failures and emits scoped gotchas. A gotcha is not “be careful with tests.” It is “When changing package exports, run the consumer fixture because unit tests do not cover ESM entrypoints.” Keep gotchas local to role, repo, or workflow. The point is to delete 95 percent of generic advice and preserve the 5 percent that changes behavior. If a gotcha has not fired in weeks, demote it. Durable memory should decay unless it keeps paying rent.

Use Structured State for Retrieval, Not Personality

Markdown is enough for continuity, but long-running systems also need queryable state. Use SQL for workflow facts that need exactness: task graph, ownership, budgets, run status, approvals, artifact paths, model used, heartbeat schedule, and verification results. Use vectors for fuzzy recall: similar prior failures, design discussions, research snippets, and domain notes extracted during interview-style discovery. Keep these stores behind narrow retrieval functions. The agent should ask, “What prior gotchas match this failing Playwright test?” not receive a giant embedding dump because a file name matched.

This is also where parallelism becomes tractable. One-agent-per-task works only if memory has ownership boundaries. Each agent gets its heartbeat, assigned files, budget, and output contract. Shared state is updated through issue records, artifact manifests, and reviewer verdicts, not through a shared monologue. If two agents need the same context, give them the same checkpoint plus separate work scopes. If they need to coordinate, make the orchestrator write the coordination fact into SQL or a project checkpoint. Do not rely on agents remembering each other’s chat trails.

Close the Loop With Verification and Cost

Memory should tighten the verification loop, not replace it. Every loop needs an executable definition of done: tests, type checks, lint, evals, visual evidence, benchmark thresholds, review scores, or artifact hashes. Require proof of work for expensive or failure-prone steps: captured logs, SHA-256 hashes of test output, Playwright videos, screenshots, or CI links. Then store only the proof summary in the checkpoint and the raw artifact path in structured state. This prevents the classic overnight failure where the agent writes a persuasive completion note but never performed the gate.

Model routing follows the same principle. Use a frontier model where judgment, planning, or ambiguous review controls downstream cost. Use cheaper or local models for narrow extraction, log summarization, heartbeat maintenance, and retrospective clustering when quality is measurable. Compress tool output before it reaches the main agent, especially logs, retrieval chunks, and repeated diagnostics. Track wall time, tokens, output tokens, cache reads, and pass rate by workflow. Cost control is not just choosing a cheaper model; it is designing memory so the best model reads less and decides from fresher evidence.

The mature version of this system is small on purpose. A long-running agent wakes, reads its heartbeat, loads the current checkpoint, queries only relevant state, acts inside a scoped task, proves the result, records the run, and promotes only durable lessons. That is the throughline: autonomy comes from disciplined forgetting. The agent resumes with enough context to continue exactly where the system left off, and not enough context to keep relitigating yesterday’s mistakes.

Key takeaways

  • Memory is runtime state, not a larger prompt; split it by authority, read frequency, and expiration.
  • Rewrite checkpoints at loop boundaries and attach evidence to important claims so resumed agents do not inherit stale assumptions.
  • Keep retrospective logs append-only, then promote only repeated, specific failures into scoped gotcha files.
  • Use SQL for exact workflow state and vectors for fuzzy recall, both behind narrow retrieval functions.
  • Parallel agents need separate heartbeats, ownership boundaries, budgets, and output contracts, not a shared transcript.
  • Control cost by compressing tool output, routing models by task risk, and measuring tokens, time, and verification pass rate per workflow.
