Use Sub-Agents Without Creating Chaos

Sub-agents are useful when they reduce shared assumptions, file conflicts, or waiting time, but they only help if you give each agent a clear lane and verify the results before combining them.

Updated June 25, 2026

Start With One Owner

Before you split work across sub-agents, understand what an agent is doing. A coding agent is a chat model connected to tools: it can read files, edit files, run terminal commands, inspect test output, and sometimes talk to external systems through MCP, which is a standard way to expose tools and data sources to the agent. Its context is the set of messages, files, commands, and results it can currently “see.” That context shapes its decisions.

A sub-agent is a second agent with its own context. That isolation is the point. If one agent forms a bad assumption early, a separate agent does not automatically inherit it. This makes sub-agents useful for independent research, alternate designs, test investigation, and parallel implementation in separate parts of the codebase. It also makes them risky: two agents can make incompatible changes, duplicate work, or solve different versions of the problem.

So keep one owner: you. Your job is not to type every line of code. It is to define the target, divide the work, decide what evidence counts, and merge only what survives review. Treat sub-agents like junior contractors in separate rooms, not like one magical larger brain.

Split Only When The Work Has Boundaries

Because sub-agents create coordination overhead, do not launch them for every task. A typo fix, a small refactor, or one failing test is usually better handled by one agent. Splitting helps when the work has natural boundaries: frontend and backend changes, three competing UI prototypes, independent bug theories, separate code review passes, or research across unrelated files.

A good split has a clear input, a clear output, and a small blast radius. For example: “Agent A: inspect the API layer and report the exact contract change needed. Do not edit files.” “Agent B: update only the React form components. List changed files and tests run.” “Agent C: act as a skeptic and check the final patch against this rubric.” Those are better than “everyone look at the app,” which invites overlap and conflicting conclusions.

Use fan-out when you want multiple independent perspectives, such as three ways to implement a feature or three theories for a flaky test. Use classify-and-act when incoming work varies, such as triaging bugs into docs, tests, backend, or design. Use adversarial verification when the first answer might be self-serving, especially after a long build. The common rule is simple: split for independence, not for excitement.

Use Isolation To Prevent File Chaos

Once the work is split, the next problem is physical: where do the edits happen? If multiple agents edit the same working directory, they can overwrite each other, mix partial changes, or make it hard to tell which change caused a failure. Git worktrees solve this by giving each agent its own checkout of the same repository. Each worktree can have its own branch, files, test runs, and experiments.

For a first-time workflow, keep it conservative. Give each sub-agent a branch or worktree and a file ownership rule. One agent owns `src/api/*`; another owns `src/components/Form*`; a third only reads and reviews. Tell them they are not alone in the codebase and must not undo unrelated changes. When they finish, require a short report: goal, files changed, commands run, tests passed or failed, and any assumptions made.

This is also where a clean codebase becomes leverage. Agents do better when modules are named clearly, tests are reliable, and interfaces are explicit. If your app has tangled responsibilities, sub-agents amplify the tangle. Before parallelizing a messy area, spend time defining interfaces and constraints. Better architecture is not just good for humans; it gives agents safer rails.

Verify Before You Merge

Parallel output is not finished output. Each sub-agent saw only part of the world, so the integration step must be stricter than a normal chat answer. Verification means checking behavior against evidence, not asking the same agent whether it feels done. Run tests. Inspect diffs. Build the app. For frontend work, capture screenshots or use browser automation to confirm the visible result. For risky flows such as payments, auth, migrations, or data deletion, mark them as human validation zones and review them yourself.

Use a verification plan before the build starts. It can be short: unit tests for the changed module, one integration path, one manual check, and one rollback concern. For complex work, assign a separate skeptic sub-agent that did not write the code. Give it a rubric: requirements, edge cases, security, regressions, and consistency with existing patterns. This reduces the “I like my own answer” problem that happens when one context writes and judges the same patch.

Avoid looping forever. “Loop until done” is useful only when done is measurable: reproduce the flaky test, make all checks pass, satisfy a screenshot comparison, or remove a specific error. If quality depends on taste, such as visual polish or product copy, use agents to generate options and evidence, then choose yourself.

Build A Repeatable Harness

The pattern becomes powerful when you stop treating each run as improvisation. A harness is the setup around the model: repo structure, prompts, worktrees, tool permissions, verification rules, local notes, and reusable skills. You can create a simple version with a project instruction file that says how to plan, when to use sub-agents, what commands verify work, and which areas require human review.

After a successful run, save the useful parts. If an agent found a reliable way to review pull requests, prototype variants, or debug flaky tests, turn that into a reusable skill or command. Include the gotchas: which tests are slow, which files are generated, which APIs are fragile, and what style the project expects. This gives future agents persistent guidance without stuffing every detail into one chat.

The central discipline is restraint. Sub-agents are not a default mode; they are a way to preserve independence where independence matters. Split the work only when the boundaries are real, isolate the execution so edits stay understandable, and verify with evidence before merging. Done this way, parallel agents do not create chaos. They give you more attempts, more critique, and more speed while you remain responsible for the final shape of the work.

Key takeaways

  • Use sub-agents for independent work, competing approaches, or separate review, not for every small task.
  • Give each sub-agent a narrow lane: clear goal, file ownership, expected output, and allowed tools.
  • Use worktrees or separate branches so parallel edits do not collide in one working directory.
  • Verify merged results with tests, diffs, builds, screenshots, or a skeptic agent using a rubric.
  • Keep human judgment for subjective or high-risk areas such as product taste, payments, auth, and data changes.
  • Turn successful workflows into reusable project instructions or skills so future agent runs start with better context.
