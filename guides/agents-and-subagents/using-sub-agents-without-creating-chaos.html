Agents & Sub-Agents

Using Sub-Agents Without Creating Chaos

Sub-agents work when they are isolated, narrowly scoped, and forced through independent review before their outputs are merged into the main line of work.

Updated June 25, 2026

Start With the Harness

Sub-agents are not a substitute for engineering judgment. They amplify the shape of the system around them: repo structure, tests, task boundaries, tool permissions, state management, and review discipline. A clean harness lets smaller or cheaper models do useful work because the environment carries more of the burden. A messy harness turns parallel agents into parallel confusion.

Before splitting work, define the interface. What files may the agent touch? What output must it produce? What tests or checks count as done? What context does it need, and what context should it not see? Treat each agent like a contractor receiving a work order, not like a teammate invited into every conversation.

The most reliable split is along natural module or workflow boundaries: planner, implementer, validator, researcher, reviewer. Avoid assigning two agents overlapping edits in the same files unless the goal is comparison rather than integration. If the task is small, keep it single-agent. Multi-agent workflows cost tokens, attention, and merge effort.

Split Work Deliberately

Use sub-agents when the work has independent branches, not just because the task feels large. Good candidates include parallel code review, competing implementation prototypes, independent research questions, flaky test reproduction, migration audits, and validation against a rubric. Bad candidates include vague product thinking, tightly coupled refactors, and tasks where every next step depends on the previous result.

A practical pattern is fan out and synthesize. Give three agents the same goal in isolated contexts, but ask for different outputs: one implementation, one simpler alternative, one risk review. Or give each agent a separate slice: API contract, UI behavior, data migration, test coverage. The root agent or human then compares outputs against requirements rather than accepting the first polished answer.

For recurring classes of work, route tasks before assigning them. A classify-and-act phase can decide whether the request is a bug fix, design prototype, research task, hygiene sweep, or review job, then hand it to the right specialized prompt or skill. This reduces goal drift because the agent starts inside the right frame.

Isolate Context and Files

The simplest way to create chaos is to run multiple agents in the same working directory. Use worktrees, sandboxes, terminal session managers, or hosted agent environments so each agent has its own filesystem boundary. Worktrees are especially useful for coding because they preserve Git history while preventing file conflicts. Sandboxed environments are better for risky execution, batch triage, or AFK review loops.

Isolation should include context, not only files. If one agent sees another agent's answer too early, it will often anchor on that answer and produce agreement instead of independent judgment. Keep research, implementation, and verification in separate context windows until synthesis time. Shared state should be structured and minimal: an outline, checklist, test result, patch summary, or benchmark table.

Managed environments and orchestration layers can help when local setup becomes the bottleneck. They can provide connectors, persistent state, background terminal sessions, queues, and status tracking. The tradeoff is trust and access control. Any remote-control URL, connector token, or hosted sandbox with repo access should be treated as a credential. Local execution keeps files close, but still requires process discipline: the host must stay awake, sessions must be tracked, and agents need clear stop conditions.

Make Agents Prove Their Work

A sub-agent should not be allowed to declare victory just because it produced a confident answer. Build validation into the workflow. For software, that means tests, type checks, screenshots, browser automation, logs, reproducible commands, or a concise explanation of what could not be verified. For research, it means separating claims from evidence and asking for uncertainty explicitly.

Loop agents are useful when the success condition is mechanical: reproduce a flaky failure, satisfy a lint rule, generate a valid artifact, or iterate on a UI until screenshots meet requirements. The loop needs a hard exit condition. Without one, the agent may churn through theories, rewrite unrelated code, or optimize for passing its own interpretation of the task.

Adversarial review is the corrective to model self-preference. Ask a separate skeptic agent to review the output against a rubric before merge. The skeptic should not be asked whether the work is good in general. It should answer specific questions: Does this satisfy the original requirement? What files are riskier now? What assumptions are unproven? What tests are missing? What would fail in production?

Synthesize Like an Engineer

The synthesis step is where the human or root orchestrator earns its keep. Do not paste together every sub-agent result. Compare them. Reject duplicates. Prefer the solution with the smallest blast radius that satisfies the requirement. If two agents disagree, inspect the underlying evidence rather than averaging their opinions.

For prototypes, use tournament-style comparison instead of a single ranked list. Compare options head to head in isolated contexts, then carry forward the winner for another round. This reduces bias toward the option described first or most fluently. For implementation, require each agent to report changed files, verification commands, known gaps, and integration notes.

Move human checkpoints toward the end when the task is low-risk and well-bounded, but keep architectural control at the front. The human should set scope, constraints, and review criteria before agents start. After that, agents can run AFK through sandboxes, worktrees, scheduled checks, or remote-monitored sessions. The final merge still needs a skeptical reader.

Key takeaways

  • Use sub-agents for independent branches of work, not tightly coupled tasks that need constant coordination.
  • Give every agent a narrow contract: allowed files, required output, verification steps, and stop conditions.
  • Isolate both filesystem state and conversation context with worktrees, sandboxes, or separate sessions.
  • Treat shared state as structured handoff data, not a shared memory dump.
  • Run adversarial verification in a separate context before trusting an agent's preferred answer.
  • Synthesize by comparing evidence, risks, and tests, then merge the smallest adequate result.
