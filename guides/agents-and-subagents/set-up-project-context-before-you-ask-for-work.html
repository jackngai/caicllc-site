Set Up Project Context Before You Ask for Work

Before you ask a coding agent to change your project, give it a durable map of how the project works, what commands prove success, and where it must not improvise.

Updated June 28, 2026

Start With Durable Context

A coding agent is different from a chat assistant because it can use tools. Tools are the abilities you grant it: reading files, editing code, running terminal commands, searching the repo, opening browser pages, or calling external services through MCP, which is a standard way to connect agents to apps and data sources. That power is useful only if the agent understands the project before it acts.

Do not put all project knowledge into one long prompt each time. Put the stable parts in a project context file such as `AGENTS.md`, `CLAUDE.md`, or whatever your agent reads automatically. Treat this file as the agent's first briefing. It should explain the product goal, the architecture, the coding style, the test commands, and the boundaries. The central habit is simple: move repeatable instructions out of chat and into the repo.

This matters because an agent has a context window, which is the limited working memory it uses while planning and coding. If you spend that memory repeating setup facts, you leave less room for the actual task. Worse, if you forget one rule in a new session, the agent may make a plausible but wrong choice. Durable context makes the agent less dependent on your memory.

Write The Router First

Once you accept that context belongs in the repo, the first file should act like a router, not a novel. A router tells the agent where to look next. At the top, state the project in a few lines: what it does, who uses it, and what kind of changes are common. Then add a folder map: `src/app` contains routes, `src/components` contains reusable UI, `db/migrations` is append-only, `scripts` holds maintenance commands. This helps the agent read the right files instead of scanning randomly.

Add local rules where they matter. For example: "Use existing form components before creating new ones." "Do not edit generated files." "New API endpoints need tests in `tests/api`." "Prefer server-side validation for billing paths." These rules are better than vague preferences because they turn judgment into checkable constraints.

Keep the file short enough to be read every session. If one area needs more detail, link to an index file inside that folder. This is the markdown version of a small wiki: a central `AGENTS.md` points to narrower files such as `docs/testing.md`, `docs/deploy.md`, or `src/payments/AGENTS.md`. Use this before reaching for heavier retrieval systems. Structured links are often more reliable than hoping semantic search finds the one paragraph the agent needs.

Give It Commands And Checkpoints

After the map, give the agent a way to prove work. Agents are strongest when a task has a verifier: a command, test, log, or review step that says whether the change worked. Add commands directly to the context file: how to install dependencies, run unit tests, run lint, start the dev server, apply migrations, and typecheck. Include the expected working directory and any common failure notes.

For a first-time agent user, this is the difference between "please fix it" and "fix it, then run the checks we trust." You can ask the agent for an implementation spec before coding: the files it expects to touch, the tests it will run, and the risks it sees. For bigger work, ask it to interview you first. That means the agent asks clarifying questions before building, so hidden business rules and edge cases become explicit.

Break large requests into small, verifiable buckets. Instead of "rebuild onboarding," use checkpoints like "add the data model," "create the form," "wire the API," and "add tests for the happy path and validation errors." This reduces the chance that the agent writes a large patch based on one bad assumption. Each bucket should have its own proof.

Set Boundaries Before Autonomy

The same context file should say what the agent must not touch. Boundaries are not a lack of trust; they are part of the operating environment. Mark high-risk areas such as payments, authentication, production config, migrations, secrets, and customer data. Tell the agent when it may edit them, when it must ask first, and what extra verification is required.

Some systems let you enforce these rules with hooks, which are checks that run before a tool action. For example, a pre-tool hook can block edits to `infra/prod` or prevent commands that delete data. Even if you do not have hooks yet, write the rule down. A written boundary gives the agent a default behavior: pause and ask instead of guessing.

Also define human validation zones. These are parts of the project where quality is partly subjective or high stakes. A button color, a pricing page message, a payment retry rule, and a data deletion flow should not all be treated the same. Automate what can be verified by tests and logs. Keep human review for taste, policy, money movement, and irreversible actions.

Make Sub-Agents Use The Same Map

Once the main agent has good context, sub-agents become safer. A sub-agent is a separate agent session assigned a smaller task, such as inspecting tests, reviewing a design, or implementing an isolated module. Because it has its own context, it can avoid being anchored by the main conversation. That is useful for parallel work, but risky if each sub-agent invents its own project rules.

The fix is to make the project context file the shared source of truth. If you ask the main agent to launch sub-agents, tell it that every sub-agent must read the repo instructions, report assumptions, and stay inside a defined file scope. Independent tasks can run in parallel, especially in separate worktrees, which are separate checkouts of the same repo that prevent agents from stepping on each other's local changes.

Over time, turn repeated wins into skills: small reusable instructions for tasks like running the test suite, reviewing a PR, updating docs, or calling an API through MCP. But start with the boring file. A clear `AGENTS.md` or `CLAUDE.md` turns a coding agent from a clever stranger into a project-aware worker. The point is not to write the perfect prompt. It is to make the project teach the agent how to behave before you ask for work.

Key takeaways

  • Put stable project instructions in `AGENTS.md`, `CLAUDE.md`, or your agent's equivalent instead of repeating them in chat.
  • Use the context file as a router: project summary, folder map, local rules, and links to deeper docs.
  • List exact verification commands so the agent can prove its changes with tests, lint, typecheck, logs, or screenshots.
  • Define boundaries for high-risk areas such as payments, auth, secrets, production config, and migrations.
  • Ask for an implementation spec or an interview before large tasks so assumptions become visible before code changes.
  • Make sub-agents read the same project context and give each one a narrow file scope or checkpoint.
