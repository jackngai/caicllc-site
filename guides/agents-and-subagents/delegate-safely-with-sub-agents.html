Delegate Safely With Sub-Agents

Sub-agents are safest when you treat delegation as controlled parallelism: small jobs, isolated context, clear evidence, and an independent review before anything lands.

Updated June 28, 2026

Start With One Orchestrator

A coding agent is different from a chat assistant because it can work inside your project. It can read files, edit code, run terminal commands, call external tools, and observe the results. That creates a loop: reason about the task, act through a tool, inspect what happened, then decide the next move. A sub-agent is another agent instance you ask to handle a slice of that work.

The safest mental model is not “more agents means more intelligence.” It is “one orchestrator, several bounded workers.” You remain the orchestrator at first. The main agent can help coordinate, but there should be one place where scope, priorities, and final judgment live. Without that, parallel agents can chase different interpretations of the same vague goal and produce changes that look productive but do not fit together.

Before launching sub-agents, ask for an implementation spec or have the agent interview you. The spec should name the goal, constraints, files likely involved, tests to run, and areas where human judgment matters. This is not bureaucracy. It is the harness around the model. A cleaner harness, including clear architecture and clear prompts, lets even ordinary agents do better work because they spend less effort guessing.

Split Only Independent Work

Once the goal is clear, split work only where the pieces can proceed without stepping on each other. Good sub-agent jobs include researching separate modules, comparing two implementation options, auditing different files for the same pattern, or asking one agent to write while another validates against a checklist. Poor jobs include “build the whole feature,” “fix whatever you find,” or assigning two agents to edit the same files without a merge plan.

A tight delegation prompt has five parts: the exact outcome, the allowed files or read-only scope, the context it should use, the evidence it must return, and the stop condition. For example: “Inspect the authentication tests only. Find where session expiry is covered. Do not edit files. Return the relevant test names and any missing cases.” That task is useful because it gives the main thread information without creating merge conflicts.

Use fan-out when you need breadth, not when you are avoiding thinking. If the job is simple, one agent is cheaper and easier to supervise. Parallelism has overhead: more tokens, more summaries, more chances for conflicting assumptions. Save sub-agents for complexity that benefits from isolated perspectives, such as codebase-wide audits, flaky debugging, or design choices where anchoring on the first answer would bias the result.

Isolate Context And Files

Sub-agents are useful partly because they do not share the same mental trail. A long chat can anchor an agent to early assumptions. A fresh sub-agent can inspect the same problem without inheriting that bias. This is why independent review works: the reviewer should not be primed to defend the author’s solution. Give it the rubric and the output, not the whole messy conversation that produced the output.

Context is the information inside an agent’s working window: prompts, files it has read, tool results, and previous decisions. More context is not always better. Too much unrelated context can blur the job. For a sub-agent, include only what it needs: the relevant files, the interface contract, the acceptance criteria, and any project conventions. If it needs external systems, explain the tool. MCP, or Model Context Protocol, is a common way agents connect to outside capabilities such as GitHub, databases, docs, browsers, or internal services through structured tool calls.

File isolation matters just as much as mental isolation. If two agents edit the same working directory at the same time, they can overwrite or confuse each other. Worktrees solve this by creating separate checkouts of the same repository, so each agent has its own file space. Use separate worktrees for parallel coding attempts, prototypes, migrations, and risky fixes. Bring changes back only after review, tests, and a deliberate merge.

Review With A Skeptic

Delegation is incomplete until someone verifies the result. The agent that wrote the code is a poor sole reviewer because it is likely to prefer its own answer. Use an adversarial review step: ask a separate agent to challenge the implementation against the spec, list failure modes, inspect tests, and identify assumptions. This is especially useful before touching high-stakes areas such as payments, authentication, permissions, data migrations, or production infrastructure.

The review should be concrete. “Looks good?” invites a shallow pass. Better: “Check whether this change satisfies each acceptance criterion. Look for missing tests, hidden coupling, unsafe shell commands, and behavior changes outside the requested scope. Cite files and commands.” For UI work, ask for browser verification, screenshots, or recorded flows. For backend work, ask for test commands, logs, and edge cases. The agent’s answer should include evidence, not just confidence.

Some workflows benefit from loops: run a test, inspect the failure, patch, and repeat until a stop condition is met. Loops are powerful for reproducible failures and validation tasks, but dangerous when the target is subjective. If success depends on taste, product judgment, or brand feel, keep a human checkpoint. Automate measurable checks. Augment subjective judgment instead of outsourcing it.

Scale Gradually

The advanced version of this pattern can run many agents across a whole codebase: one per module, one per file family, or one per hypothesis. That can help with migrations, audits, or broad refactors. But the beginner-safe version is smaller: one main agent, one or two sub-agents, isolated scopes, and a reviewer. Learn the rhythm before multiplying it.

A practical first workflow is simple. Ask the main agent to draft a spec. Launch one read-only sub-agent to inspect relevant code. Launch another to propose risks or tests. Have the main agent implement the smallest coherent change. Then use a separate reviewer agent to grill the result against the spec. Finally, you inspect the diff and run the verification commands yourself or have the agent run them while you review the output.

Sub-agents do not remove responsibility. They move you from typing every line to designing the work system: scope, isolation, evidence, and review. That is the central safety rule. Delegate only when the task can be made small enough to verify. The point is not to have many agents moving fast. The point is to have independent workers produce checkable results without losing architectural control.

Key takeaways

  • Use one orchestrator to own scope, priorities, and final decisions.
  • Give each sub-agent a narrow job with allowed files, expected evidence, and a stop condition.
  • Use isolated context to reduce anchoring, and isolated worktrees to prevent file conflicts.
  • Reserve parallel agents for work that is independent, complex, or benefits from multiple perspectives.
  • Review agent output with a separate skeptic using a concrete rubric and verification commands.
  • Automate measurable checks, but keep human judgment for taste, product risk, and high-stakes changes.
