Give the Agent the Right Project Context

A coding agent edits better when your repository contains a small, reliable map of what matters, where to look, and what rules must not be broken.

Updated June 25, 2026

Start With A Router File

A coding agent is not just a chat model. It can read files, edit them, run commands, and sometimes call other tools such as test runners, package managers, search utilities, or external connectors. That power makes context more important than clever prompting. If the agent has to infer your architecture from scattered files, it may edit the wrong layer, ignore local conventions, or run expensive searches before it understands the project.

Create one root file that acts as the agent's front door. In many tools this is named `AGENTS.md`, `CLAUDE.md`, or a project rules file. The exact name depends on the agent, but the job is the same: tell the agent what the repo is, how work is organized, what commands are safe to run, and which rules apply before editing. Keep it short enough that it will actually be read into the context window, which is the limited working memory the model sees while it reasons.

A useful router file answers four questions: What is this project? Where should the agent look first? How should it verify changes? What should it never touch without permission? For example, it might point backend work to `server/README.md`, frontend work to `web/AGENTS.md`, tests to `docs/testing.md`, and deployment rules to `infra/AGENTS.md`. This is not documentation for humans only. It is an operating manual for a worker that can act.

Write Rules That Shape Behavior

Once the agent knows where to begin, the next step is to give it lightweight rules that reduce bad guesses. Good project rules are specific and operational. Instead of saying "write clean code," say "use existing service objects in `app/services` before adding new framework patterns." Instead of "test your work," say "run `npm test -- --runInBand` for frontend changes and `pytest tests/api` for API changes." The agent needs actions, not values.

Include coding style, commit expectations, naming conventions, test commands, and known hazards. Add "never do" rules for critical paths, generated files, secrets, migrations, production data, or vendored code. These rules matter because agents can use tools. A tool is any capability outside plain text generation, such as editing a file, running `rg`, applying a patch, or executing a test command. If a tool can change the project, the rule should be clear before the tool runs.

The failure mode is overloading the file with every preference you have. Long rule files dilute the signal and waste context. Put only evergreen rules in the root file: architectural boundaries, safety constraints, verification steps, and routing. Put details closer to the folder that owns them. The root file should guide the agent to the right next file, not become a full wiki.

Add Folder Notes And Indexes

After the root router, add local notes where context changes. A folder-level `AGENTS.md` or short `README.md` can explain the purpose of that directory, its dependencies, common edit paths, and tests that cover it. This helps because agents usually work by reading a small set of files, forming a plan, then editing. If the folder note says "state lives in `store.ts`, UI components are dumb, API calls go through `client.ts`," the agent is less likely to scatter logic across the wrong files.

For larger projects, add indexes. An index is a plain markdown map with links to important files and short descriptions of when to use them. This is often more reliable for first-time agent work than semantic search or vector retrieval. Semantic search can help when the codebase is huge and keywords fail, but an explicit index gives the agent a drill-down path: start here, then go there, then verify with this command.

A practical pattern is to organize indexes around the questions you expect to ask. For example: "How do I add a new API endpoint?" links to routing, validation, service, tests, and examples. "How do I change billing UI?" links to components, data fetching, permissions, and screenshots. This turns hidden team knowledge into readable context without forcing the agent to inspect the whole repo.

Use Specs Before Big Edits

Context files help the agent understand the repo, but they do not replace a task spec. For anything larger than a small fix, ask the agent to break the work into small, verifiable buckets before it edits. A spec should state the goal, affected areas, acceptance checks, and open questions. This gives the agent a target and gives you a checkpoint before code changes begin.

A good first-agent workflow is: read the router file, inspect the relevant folder notes, ask clarifying questions, propose a short plan, then edit. The clarifying step is not wasted time. It is how the agent pulls business intent out of your head before it makes technical choices. If the goal is "improve signup," the agent needs to know whether success means fewer clicks, better validation, accessibility, conversion tracking, or backend reliability.

Verification should be part of the spec, not an afterthought. The verifier can be a test suite, a lint command, a build, logs from a running app, or even a second model reviewing the patch. For beginners, start with ordinary commands the agent can run locally. The point is to make success observable. An agent with project context and no verifier can still produce plausible wrong code.

Scale Context Before Scaling Agents

Sub-agents are separate agent workers that can handle smaller tasks in parallel, such as investigating one module while the main agent edits another. They are useful only when the project context is already clear. Without shared rules and indexes, parallel agents multiply confusion. They may duplicate work, choose conflicting patterns, or edit overlapping files.

If you do use sub-agents, give them narrow ownership: "inspect the test failures in `api/` and report likely causes," or "update only docs under `docs/billing/`." For heavier parallel work, teams often use isolated worktrees or cloud agents so each worker has its own checkout and does not fight the local environment. That is an advanced move, but the principle is simple: clear boundaries first, parallelism second.

MCP, or Model Context Protocol, fits into the same idea. It is a way for agents to connect to outside systems and tools, such as issue trackers, docs, databases, or code search. MCP can provide richer context, but it should not be your first fix for a messy repo. Start with durable markdown context, folder notes, and verification commands. Then add external tools where they answer a real question the files cannot.

The central habit is to treat context as part of the codebase. Your first win is not a giant memory system or ten agents running at once. It is a repo that can tell an agent: here is what this project is, here is where to look, here is how to work, and here is how to prove the change is right.

Key takeaways

  • Put a short `AGENTS.md`, `CLAUDE.md`, or project rules file at the repo root as the agent's routing map.
  • Write rules as concrete actions: where to edit, which commands to run, and what paths require permission.
  • Use folder notes and markdown indexes to give the agent reliable drill-down paths through the repo.
  • For larger tasks, ask for a small spec with checkpoints before allowing edits.
  • Do not scale to sub-agents or MCP until the basic project context is clear and durable.
