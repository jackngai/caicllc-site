Agents & Sub-Agents

Building Skill Libraries for Reliable Agent Work

Reliable agent work comes from packaging the parts humans usually repeat: procedures, scripts, templates, edge cases, and objective checks that an agent can discover and run at the right moment.

Updated June 25, 2026

What Belongs in a Skill

A useful skill is not a clever prompt. It is a small operating manual plus a folder of reusable machinery. The manual tells the agent when the skill should fire, who it is for, what inputs it needs, what output it should produce, and which failure modes matter. The folder holds scripts, templates, examples, configuration, reference files, and verifiers.

The most productive split is four skill types. Utility skills perform a repeatable task, such as running an API workflow, converting a document, extracting frames from a video, or preparing a test fixture. Verification skills grade output against objective criteria. Data enrichment skills pull in external context, such as code graphs, repo memory, OCR output, or a knowledge base. Orchestration skills chain tools and subagents across a larger job.

That split prevents a common mistake: stuffing every instruction into one mega-skill. A code review skill, for example, should not also own repository indexing, security scanning, frontend taste checks, and CI diagnosis. It can call those skills, but each should remain independently testable. Smaller skills are easier to trust because their inputs, outputs, and failure modes stay visible.

Put Determinism in Scripts

Agents are strongest when they reason over ambiguous context, but many parts of a workflow should not be left to model judgment. Calculations, file conversion, API calls, table extraction, transcript retrieval, scene detection, lint checks, and scoring rubrics belong in scripts. This saves tokens, removes variation, and gives the agent a concrete result to inspect.

A media analysis skill illustrates the pattern. The agent should not decide by vibes which video frames matter. A script can use scene detection to capture frames only when the visual content changes, then use caption extraction first and fall back to transcription when captions are unavailable. The skill document can tell the agent how to interpret the transcript and frames, but the collection step should be deterministic.

The same applies to coding. A codebase intelligence skill can rely on an index, knowledge graph, or semantic map instead of repeatedly asking the model to scan files from scratch. A document skill can convert PDFs and Office files into structured markdown while preserving tables before RAG or summarization. A security skill can run scanners against third-party skill packs before installation. The agent’s job becomes deciding what evidence matters, not reinventing the evidence-gathering process every run.

Design the Trigger Carefully

The description at the top of a skill is not marketing copy. It is the routing layer. Write it as a precise trigger: use this skill when the agent must perform X, for Y audience, under Z conditions. Avoid broad descriptions such as “helps with frontend work.” Prefer “Use when implementing or reviewing generated frontend UI where layout, typography, motion, or browser screenshots must be checked against project taste constraints.”

Good triggers reduce both underuse and overuse. A verification skill should fire when output quality can be graded objectively. A taste-oriented skill should fire when subjective design judgment is required, but it should not pretend to fully automate taste. A repository graph skill should fire when the task crosses module boundaries or the codebase is too large to fit cheaply in context. A simple one-file fix probably does not need it.

Persistent configuration also matters. Skills can include config files for project defaults, preferred commands, source directories, model choices, or user-specific constraints. When a decision cannot be inferred safely, the skill should ask a structured question rather than guessing. This keeps the skill reusable without baking in assumptions that only fit one project.

Make Verification a First-Class Skill

Verification skills usually produce the highest quality gain because they create a second layer that is less interested in producing output and more interested in falsifying it. The best verifiers return objective pass or fail signals: tests passed, schema valid, screenshots nonblank, links reachable, transcript extracted, security scan clean, latency below target, tables preserved, claims backed by provided sources.

For coding agents, a verification plan should exist before major implementation begins. The plan can specify automated tests, static checks, browser inspection, screenshot comparison, CI confidence scores, and human validation zones for high-stakes areas such as payments, auth, legal copy, or production data migration. The human zone is not a failure of automation. It is an explicit boundary where judgment or risk ownership still belongs to people.

Verification should also include “gotchas.” Every time a skill fails in a memorable way, add the failure to the skill: flaky command, misleading file name, common hallucinated API, screenshot overlap, table loss during conversion, bad OCR on scanned PDFs, prompt injection risk in a third-party repo, or the model’s habit of over-designing a dashboard. Gotchas turn painful exceptions into reusable guardrails.

Compose Skills Into Agent Workflows

Skills become more valuable when they can be composed. A serious research workflow might convert documents to markdown, OCR spatial regions from PDFs, enrich with notes from an Obsidian knowledge base, then run a source-grounded verifier. A coding workflow might load project rules, query repo memory, launch subagents in separate worktrees, run tests, request CI review, and create a gotcha entry from any failure.

Long-running loops need special care. A loop should have a trigger, an action, and an end condition, such as “sweep documentation overnight until every public API has an example and the verifier passes.” Without an end condition, loops produce operational debt: lots of changes, unclear value, and hidden cleanup work. Use stronger reasoning models for planning and architecture, faster models for repetitive implementation, and subagents only when work can be split cleanly.

Before adopting third-party skills, treat them like code dependencies. Scan them for prompt injection, data exfiltration, privilege escalation, and supply-chain risk. Read the scripts. Check what tools they can call. Prefer skills that expose deterministic behavior and verifiable outputs over opaque prompt packs. A skill library should make agents more reliable, not merely more autonomous.

Key takeaways

  • Package repeatable work as folders with trigger docs, scripts, templates, examples, config, gotchas, and verifiers.
  • Keep deterministic operations in scripts so the model spends context on judgment rather than mechanics.
  • Write skill descriptions as routing triggers, not summaries, and make them narrow enough to avoid accidental misuse.
  • Prioritize verification skills with objective pass or fail checks before adding more generation skills.
  • Record gotchas after real failures so the library improves through use.
  • Treat third-party skills as dependencies: inspect, scan, and constrain them before giving agents access.
